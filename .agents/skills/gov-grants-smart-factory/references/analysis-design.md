# 분석·설계 8종 작성 안내

필요한 역할의 절만 읽는다. **양식**은 로컬 V2.0 원문 지침 요약, **관행**은 전문가 한 사업의 관찰, **작성/QA**는 이를 이번 사실에 적용하는 권고다. 모든 역할의 제공 사실·서명·승인·실행은 별도 확인한다. 숫자/폰트/장비·반복 개수는 고정 규칙이 아니다.

원문 지침·SHA·XPath는 repo `resources/stage1/analysis-design-rules.json`의 아래 rule_id, 상세 구조는 `resources/stage1/analysis-design.md`에서 확인한다. 개별 참고자료의 관측·반례·판정은 비공개 로컬 입력에 보존한다. 공개 안내는 그 자료의 실제 회사·업무값을 포함하지 않는 일반 작성 원칙이다. 자원은 이 스킬의 `scripts/run.py path <repo상대경로>`로 찾는다.

## SF-AD1 현행업무분석서

**양식:** 현행 업무와 현행 시스템을 나눈다. 기업 소개·전체 업무/부서 연결·주요 공정 세부 흐름·문제/이슈, 기존 H/W·S/W·N/W 구성/메뉴·재활용 방안을 제시한다. 근거 `SF-AD1-s1-p4~18`.

**관행:** 기업 소개→전체 AS-IS→업무별 도식+번호 설명→문제/이슈 표→정보화 재고표. 도식과 설명을 한 블록으로 묶는다.

**입력/작성:** `project.customer`, `business_profile`, `business_processes.current_steps/issues`, `systems.as_is_description/configuration`, 현재 메뉴·장비와 출처. 부재와 미조사를 구분하며 “시스템 없음”도 사업 사실이 필요하다. 공정별 행위 주체·입출력·다음 공정을 구체화한다.

**피할 오류/QA:** 자료 내부의 기업 연혁·설명되지 않은 강조 표시·작성 기준일 차이를 확인한다. 현재 구성과 목표 구성을 섞지 않고 현행 문제→요구사항 연결 및 도식/설명 대응을 검토한다. 원문 명칭/연도는 자동 정정하지 않는다.

## SF-AD2 요구사항정의서

**양식:** 사업계획/착수/산출내역과 협의에 근거한 상세 요건·제약을 기능/비기능으로 구분한다. 추가·변경 기능과 장비 종류별 비기능 상세를 다루며 ID·유일 명칭·요약·요건·전제·도입기업 담당자·출처를 작성한다. 근거 `SF-AD2-s1-p4~18`. 여기의 분류 지침은 선택한 양식의 범위로 읽는다.

**관행:** 요구 1건의 상세 카드에 요약→요구사항→업무 프로세스/메뉴 경로→전제조건→담당자→출처를 반복한다.

**입력/작성:** `requirements`의 system/business_area/kind/change_type/description/details/constraints/owner와 source_refs. 대상·입력 필드·처리/계산·저장/조회·오류 조건을 명확히 하고 변경 전후를 구분한다. 기능/비기능과 기존/추가/변경/삭제는 별개다. 원문에 전용 변경구분이 없으면 이름에서 확정하지 않는다.

현재 AD2 프로필은 제공된 `kind`에 따라 기능→비기능→유형 미확인 순서로 상세 카드와 목차를 묶고 각 그룹 안의 입력 순서를 보존한다. 비어 있는 그룹은 생략하고 남은 그룹 번호만 연속 부여한다. `null`을 비기능으로 추정하거나 명시 요청 없이 ID·원문 분류를 바꾸지 않는다. 이는 선택한 원본의 기능/비기능 분리 지침을 구현한 것으로 다른 양식의 보편적인 분류 규칙이 아니다. 사용자가 선택 범위·시작 번호·순서를 지정하면 아래의 선택 원장과 이전→새 ID 대응에 따라 적용한다. 목차 갱신도 실제 카드의 순서와 소유 문단을 따라야 하며 비목차 본문을 보존한다.

**피할 오류/QA:** 목차와 본문 ID·명칭이 다르면 원문 이슈로 보존한다. 목차·카드·추적의 ID/명칭과 담당자·근거를 대조한다. 상세 카드 전체를 의미 반복 단위로 다루되 원본의 장비·담당자를 새 사실로 복사하지 않는다.

검토본에서 요구 ID를 바꿨다면 해당 카드의 명칭·기능/비기능·일련 항목을 기준으로 이전→새 ID 대응을 만든다. 목차, 다른 카드의 제약 참조, 기능대비표와 설계서의 연결까지 실제 대상과 대조한다. 일부 접두어만 일괄 치환하거나 옛 ID가 같은 문서에 남은 상태를 새 표준으로 학습하지 않는다. 사용자가 채운 담당자·직위와 의도적으로 비운 기타사항은 해당 카드에 보존하며, 다른 사업의 담당자 기본값이나 모든 비고 칸의 삭제 규칙으로 확대하지 않는다.

### 기능 범위와 구축·납품 비기능 요구사항

선택한 기능 요구사항 수 `N`과 구축·납품 비기능 요구사항 수 `M`, 문서 전체 수 `N+M`을 별도로 집계한다. 신규·수정개발의 합계가 기능 선택 범위에 관한 것인지 먼저 구분하고, 비기능을 기능 신규개발 건수에 더하지 않는다. 사용자가 비기능을 제외했다면 자동 추가하지 않는다. 이후 사용자 검토본에 비기능 카드가 추가되고 그 검토본 기준의 재작성을 요청했다면 추가 범위를 보존하고 이전 기능 전용 입력으로 되돌리지 않는다. ID·순서·목차와 카드별 유형은 최신 확정 범위에 대응한다.

구축·납품 카드는 사업계획상 대상과 목적을 짧게 설명한 뒤, 근거가 있는 도입·구축 목록, 설치 장소·환경의 전제조건, 검수 시 확인할 문서·항목을 기존 카드 안에 배치한다. 목록은 제공된 본문 표나 그림을 사용할 수 있으며 품목·규격·수량·단위와 해당 근거를 대조한다. 그림의 표를 다시 만들려고 카드의 행·열·병합을 바꾸지 않는다. 검토본이 목록 그림을 넣었다면 그림의 실제 항목도 읽어 대응하고, 텍스트 추출에 목록이 없다는 이유만으로 미작성으로 판정하지 않는다.

HW 범위는 해당 사업의 도입목록에 따라 생산설비와 IT 장비를 구분하여 포함한다. SW는 도입 모듈·라이선스 등 자료에 있는 범위를 쓰고, NW는 물리 공사·통신장비·데이터 수집 엔지니어링을 구별한다. 공란인 공사 행이나 포괄적인 카드 제목에서 케이블·설치 위치·구축 수량을 추론하지 않는다. 설치환경 점검과 검수확인서 확인은 충족해야 할 요구이며, 실제 설치·검수 완료 또는 서명·승인 사실로 바꾸지 않는다.

기존 기능의 내용이 유지된 검토는 요건·산식·업무 절차를 새로 고칠 지시로 해석하지 않는다. 사용자가 비운 출처 칸은 그대로 두고 근거 SHA·쪽수·XML 위치는 연결 원장에 보존한다. 추가 카드와 기존 카드의 서식이 다르면 그 차이를 기록하되 특정 글꼴·줄간격의 혼재를 재사용 규칙으로 만들지 않는다. 수정본 기준 재작성은 현존 역할별 서식을 보존하고, 별도 서식 정리 요청이 있으면 해당 범위에서 일관성을 검토한다. 그림·서명의 보존 범위와 기준본 확인은 `$hwpx-authoring`의 `references/review-feedback.md`를 따른다.

### 사업계획 기능표에서 작성 단위 확정

사업계획서의 `Application 시스템 기능 설명` 등 지정 기능표에서 특정 `구분`만 작성하도록 요청받으면, 먼저 사용자가 확정한 작성 단위를 확인한다. 기능명 묶음 수와 하위 `등록/실행/조회` 단위프로세스 행 수는 별도로 집계한다. 기능명 묶음 기준으로 확정한 경우 한 기능의 하위 동작은 한 요구사항 안에 함께 작성하며 자동으로 여러 요구사항으로 분할하지 않는다. 단위프로세스별 분리는 사용자가 그 단위로 작성하도록 명시한 경우에만 적용한다. 원문에 여러 행이 있다는 사실이나 개별 구분 셀의 수만으로 작성 건수를 확정하지 않는다.

생성 전에 선택 원장을 고정한다. 원본 SHA·OPF 구역·표/행/셀 XPath, 병합된 모듈·기능명·설명의 소유 관계, 선택 단위와 포함된 모든 하위 행·원문 구분, 선택/제외 근거, 요구 ID와 기존 요구 참조를 남긴다. 사용자 확정 단위의 구분별 수와 총수 `N`을 검산하고, 단위프로세스 행 수는 별도 수치로 기록한다. 같은 이름의 기능도 모듈·원문 소유 범위가 다르면 이름만으로 합치지 않는다. 기존 항목이나 비기능 제외는 사용자가 지정한 범위에만 적용한다. 특정 사업의 건수·접두어·구분 명칭을 모든 후속 사업의 기본값으로 만들지 않는다.

선택 원장의 순서로 `N`건의 카드와 목차를 작성한다. 기존 요구 ID는 보존하며, 요구사항 재번호를 명시한 경우에만 지정한 시작값과 이전→새 ID 대응에 따라 변경한다. 기능 묶음 카드에는 원문 기능명과 해당 기능의 등록·실행·조회 등 모든 선택 동작을 유지한다. 단위프로세스별 작성이 명시된 경우에는 이름에 해당 동작을 표시해 구별한다. 각 카드의 요약·요건·업무 처리절차·제약/전제·담당자·출처를 확정 단위에 맞춘다. 등록의 입력·검증·저장, 실행의 처리·생성·계산, 조회의 조건 선택과 기존 정보 표시를 구분하되, 동작 설명의 구분을 카드 분리 지시로 해석하지 않는다. 공통 설명·조건은 관련 카드에 유지하고 미확인 산식·연계·적용 범위를 확정 사실로 바꾸지 않는다.

완료 전 선택 원장의 확정 단위마다 정확히 한 카드가 있고 포함된 모든 하위 행의 동작·제약이 그 카드에 반영됐는지 확인한다. 제외 범위 유입, 본문·목차의 ID/명칭/순서와 구분별 합계도 대조한다. 출처 칸은 사용자 검토본의 공란을 보존하는 경우를 제외하고 독자가 찾을 수 있는 기능명·표·행 범위와 구분을 간결하게 쓰며, 전체 SHA/XPath는 연결 원장에 남긴다. 확정 건수에 따라 양식의 상세 카드를 반복할 수 있으나 카드 내부의 행·열·병합·고정 라벨은 바꾸지 않는다. 문체·글꼴·줄바꿈 검토는 [editorial-quality.md](editorial-quality.md), 설계 연결은 아래 [요구사항별 설계 대응](#요구사항별-설계-대응)을 함께 따른다.

## SF-AD3 기능대비표

**양식:** 도입 솔루션/기존 시스템 기능을 기준으로 기존(재활용)·추가·변경·삭제를 나누고 추가/변경/삭제의 내용·협의 근거를 제시한다. 비용 산출내역 기능 누락도 확인한다. 근거 `SF-AD3-s0-p29~36`.

**관행:** 대/중/소분류를 시스템/모듈/기능으로 구체화하고 각 기능을 대상 정보+관리/조회/등록 행위로 간결하게 설명한다.

**입력/작성:** `features`의 분류·change_type·description·before/after·requirement_ids·meeting_ids/evidence_ids. 변경 기능은 초기 동작과 바뀌는 동작을 모두 쓴다. 분류 그룹과 기능행 반복/병합을 구분한다.

**피할 오류/QA:** 참고의 빈 비고·전후 설명 부족·다른 사업 잔여 머리말을 관행으로 복제하지 않는다. 기능 총수/분류별 수·ID·요구/비용 원장 커버리지를 검산한다. 원자료가 없으면 완전성은 판정불가다.

기능명·분류·동작 설명과 내부 분석용 관리키를 구분한다. 사용자가 소분류의 관리키와 반복되는 적용 확인 안내를 제거했다면 기능명·변경구분·설명·공식 요구 참조를 남긴 간결한 구성을 따른다. 제거한 키와 전체 추적 관계는 비공개 원장에 보존한다. 단독으로 남은 키는 일관성 확인사항으로 기록하고, 필수 식별자나 양식의 추적 칸까지 지우는 관행으로 삼지 않는다. 같은 열·셀·병합을 유지한 사용자 열폭 재배분도 검토본의 직접 수정이므로 다음 작성에서 보존한다.

## SF-TD1 개선업무설계서

**양식:** 개선된 전체 흐름과 주요 공정의 2~3단계 세부 흐름, 개선 구분, 현행 문제 해결과 기대효과를 작성한다. 근거 `SF-TD1-s1-p4~9`.

**관행:** 전체/업무별 TO-BE 도식+번호 설명 뒤에 업무명/AS-IS/TO-BE/기대효과 표를 둔다. 조건 분기·창고 이동·연동·등록 시점을 구체화한다.

**입력/작성:** `business_processes.current_steps/target_steps/issues/expected_effects/requirement_ids`와 도식 자료. 현행 문제→개선 행위→관찰 가능한 기대효과를 연결하고 개선 부분의 범례를 정한다. 실측 성과와 기대효과를 구분한다.

**피할 오류/QA:** 중복 절차나 문서 간 대상 범위 차이는 적용 범위·개정 이력으로 확인한다. 도식·번호 설명·요구·개선 구분이 맞는지 검토하며 “실시간/자동”은 실제 설계 근거가 필요하다.

## SF-TD2 아키텍처설계서

**양식:** 전체/HW/SW/NW 구성도, 도입 장비의 모델·세부규격·설치 일정·객관 검증방안과 해당시 클라우드 제공 내용을 작성한다. 근거 `SF-TD2-s1-p4~20`.

**관행:** 도식과 의도 설명→HW 도입/검증표→SW 설치표→NW 공사표. 그림에 장비 키·신규/기존·연결/현장 위치를 표시한다.

**입력/작성:** `systems`와 `deployment_items`의 계획 규격·수량·일정·검증 방법, 클라우드 실제 사용 여부. 장비 키로 구성도·본문·명세·AD2·TI2를 연결한다. 기술/주소/토폴로지는 이번 사업에서 제공된 사실만 쓴다.

**피할 오류/QA:** 시스템 설명과 검증 방안, 문서별 장비 모델·사양이 다르면 승인 변경인지 미확인으로 남긴다. SW/NW 검증방안을 누락하지 않으며 실물 확인 결과를 계획서에서 미리 확정하지 않는다.

사용자가 특정 구성 항목을 `해당사항 없음`으로 정했다면 그 적용 범위를 해당 사업의 확인된 입력으로 보존한다. 자료 미제공을 근거로 비해당을 추정하거나 다른 사업에도 같은 구성을 강제하지 않는다. 반복되는 확인 안내를 덜어낸 편집과 실제 사양·설치·개통·검증이 확인된 사실도 구분한다.

## SF-TD3 화면설계서

**양식:** 화면/팝업 표준, 역할별 메뉴 구조/권한, 화면별 상세, 검토 결과를 작성한다. 변경은 전후 화면/내용을 구분하고 처리순서·버튼·필수 입력·요구 제약과 실제 검토/승인 근거를 제시한다. 근거 `SF-TD3-s0-p60~73`.

**관행:** 표준→권한표→화면 상세 카드→검토표. 상세는 설명/추가 컬럼/절차/필수 입력/버튼/체크로 나눈다.

**입력/작성:** `screens`의 ID/name/path/menu_levels/fields/buttons/steps/checks/permissions, 요구/기능/프로그램 연결, 실제 전후 그림·review_ids. 캡처가 없으면 그림·시안 확인 상태만 표시하고, 근거가 있는 화면 구성·입력·버튼·검증·권한 설계는 충실히 작성한다. 실제 구현/승인 그림은 만들지 않는다. 실작성과 실제 수행 확인의 구분은 [facts-and-writing.md](facts-and-writing.md)를 따른다.

캡처가 제공되면 로그인·공통 구성·팝업·개별 화면의 역할을 구분하여 지정 영역에 배치하고, 카드의 ID·명칭·메뉴와 이미지 안의 제목·선택 메뉴·경로를 맞춘다. 이미지별 SHA·삽입 위치·대응 화면을 원장에 남기며, 같은 이미지가 서로 다른 화면 카드에 쓰이면 공통 화면인지 오삽입인지 직접 확인한다. 이미지가 들어갔다는 이유만으로 대응 검사나 필수 화면 설명을 완료 처리하지 않는다. 미연결·조회 실패·빈 목록·미승인·비활성 버튼이 보이는 캡처는 관측된 상태로 기록하며 정상 조회·기능 가동·승인 완료로 바꾸어 해석하지 않는다.

사용자가 임시 기존/변경화면 표식과 반복 확인 문구를 캡처로 대체했다면 그 구성을 유지한다. 별도 추가했던 버튼 동작 목록·연계 코드 나열을 본문에서 정리한 경우에는 처리순서·입력/표시 항목·주요 체크를 중심으로 읽히게 작성하고, 제거한 블록을 자동 복원하지 않는다. 다만 고정 양식의 필수 칸과 실질 동작·필수값·오류/권한 조건은 보호한다. 버튼 이름만 보이는 그림이 처리 결과나 제한 조건 전체를 설명한다고 보지 말고, 필요한 명세의 문서 내 위치와 전체 요구·기능·프로그램 연결을 별도로 보존한다.

**피할 오류/QA:** 목차 번호·검토ID·상세ID·명칭의 불일치나 미완성 절차를 모방하지 않는다. 카드·메뉴·검토의 ID와 필수값/버튼/체크 대응, 그림 가독성/분할을 확인한다. 가상 시안은 실제 화면/승인이 아니다.

선택한 TD3 V2.0 원본 `Contents/section0.xml`의 ID 지침은 시스템명3자리+문서명3자리+일련번호3자리(예: `MES-TD3-001`)다. 제공 ID가 이 형식과 다르면 원본 지침과의 차이를 manifest 경고로 남기고 ID는 보존한다. 합성 접두어나 다른 사업의 ID를 임의 교정하지 않는다. 이 원본별 경고를 현행 사업 전체의 규칙 위반 판정으로 일반화하지 않는다. 현재 프로필은 화면 상위 `source_refs`를 인쇄하므로 필드·버튼·권한별 개별 출처는 SHA로 연결한 원입력 JSON을 별도 검토한다.

## SF-TD4 프로그램설계서

**양식:** 전체 목록과 추가/변경 모듈별 ID·유일 명칭·요약·모듈/테이블 데이터 흐름·기능·인터페이스·관련 테이블을 작성한다. 근거 `SF-TD4-s0-p40~48`.

**관행:** ID/요약/데이터흐름/조건/필드/버튼/절차/테이블을 반복하고 도식 선 범례로 선택·조회·삽입·수정·SQL 흐름을 구분한다.

**입력/작성:** `programs`의 기능·조건·인터페이스·계산 규칙·테이블/화면/요구 연결과 실제 설계 자료. 프로그램명에 맞는 데이터·처리·출력·오류 경로를 상세화한다.

요구사항별 동일 번호의 설계를 요청받으면 아래 [요구사항별 설계 대응](#요구사항별-설계-대응)에 따라 공용 프로그램과 요구별 설계 항목을 구별한다.

**피할 오류/QA:** 프로그램 제목과 다른 업무의 로직이 복사된 경우 정답으로 학습하지 않는다. ID 존재 외에 이름·요구·화면·도식·테이블·기능의 의미 일치를 읽고 검토한다. 미확인 산식을 추측해 정상으로 만들지 않는다.

## SF-TD5 데이터베이스설계서

**양식:** 전체 테이블 목록과 추가/변경 테이블 상세, 설명명·영문 물리ID·타입/자리수·PK/FK·null·암호화 대상/알고리즘을 작성한다. 구현된 물리DB의 Excel 추가 제출 지침도 있다. 근거 `SF-TD5-s0-p40~53`.

**관행:** 테이블/컬럼을 행으로 반복하고 기본값 열을 추가해 기술한다. 추가 열은 한 사례의 선택이며 현재 양식 의미를 대체하지 않는다.

**입력/작성:** `database_tables/columns`와 실제 schema/export, 타입·길이/precision/scale·key·nullable·default·encryption 정책, 외래키. 논리명과 물리ID를 분리한다. 실제 export가 없으면 논리 설계/미확인으로 표시하며 “물리DB 제출 완료”를 주장하지 않는다.

요구사항별 동일 번호의 설계를 요청받으면 아래의 대응 원장을 사용한다. 설계 항목 건수와 서로 다른 물리 테이블 수는 별도로 집계한다.

**피할 오류/QA:** 참고의 컬럼명/ID 전치·테이블ID 중복·nullable/암호화 미확인을 복사하지 않는다. 테이블별 컬럼ID 유일성·FK 대상·타입/길이·목록/상세 건수·물리자료 연결을 검사한다. Excel의 존재/출처도 별도로 확인한다.

## 요구사항별 설계 대응

사용자가 요구사항별로 TD4·TD5를 같은 일련번호와 같은 건수로 맞추도록 지정하면 확정한 AD2의 선택 원장을 공통 순서로 삼는다. 확정 요구 한 건에 프로그램 설계 항목 한 건과 DB 설계 항목 한 건을 두고 TD4·TD5의 순번을 대응시킨다. 기능 묶음으로 확정한 요구는 설계에서도 같은 묶음을 유지한다. 원래 AD2 ID가 불연속이더라도 설계 항목 순번에 맞춰 바꾸지 않고 별도의 출처 참조로 보존한다. AD2까지 재번호하도록 명시한 경우에만 요구 ID를 함께 변경한다. 이 대응 방식은 사용자 지정 작성 방식이며 모든 양식의 기본적인 일대일 관계로 일반화하지 않는다.

대응 원장에는 `ordinal / 원본 requirement_id / program_design_id / database_design_id / 확정 기능·하위 동작 / 공용 program_id / 공용 table_id / 데이터 조작 / 설계 근거`를 구분한다. 순번·원본 요구 ID·문서의 설계 항목 번호·실제 프로그램/테이블 ID는 서로 다른 식별자다. 공용 자원을 여러 요구가 사용하면 그 자원 ID를 유지하고 각 요구별 사용 목적·조건·입출력·읽기/쓰기 범위를 별도로 작성한다. 요구 개수에 맞추려고 독립 프로그램·물리 테이블을 같은 수만큼 새로 만들거나 같은 테이블의 키·타입·제약을 카드마다 다르게 쓰지 않는다. 설계 제안은 구현된 자원과 구분한다.

TD4의 각 항목은 해당 요구의 조건·입력→처리→출력/오류와 관련 테이블을 설명한다. TD5의 각 항목은 해당 요구에 쓰는 테이블·컬럼·관계와 조회/저장 범위를 설명하고, 공용 스키마 상세는 동일한 자원 정의에 연결한다. 조회와 실행이 같은 테이블을 쓰더라도 조회 요구에 생성·수정 처리를 덧붙이지 않는다. 필요한 상세를 공용 정의로 모았으면 문서 안에서 그 정의의 ID/위치를 찾을 수 있어야 하며, 참조 한 줄만으로 요구별 데이터 조건 설명을 대신하지 않는다.

선택한 양식의 기존 ID·명칭·설명·참조 칸에서 설계 번호와 요구 ID를 식별 가능하게 작성한다. 물리 ID 칸을 설계 항목 번호로 대체하거나 대응표를 넣으려고 열·셀·소제목을 추가하지 않는다. 상세 카드 반복이 허용되는 단위와 공용 정의의 기존 배치 위치를 먼저 확인한다.

최종 검증은 확정 요구 `N`건과 TD4·TD5 각각의 `N`개 순번·누락·중복, 원본 요구 ID 참조, 목록/목차/상세의 ID·명칭을 대조한 뒤 각 순번의 모든 하위 요구 동작·프로그램 처리·DB 데이터 조작이 의미상 일치하는지 읽는다. 공용 자원 정의의 일관성, 현재 출력의 모든 카드·계속 쪽·마지막 항목까지 별도로 확인한다. 번호와 건수 일치만으로 요구 충족이나 구현·시험 완료를 판정하지 않는다.
