# 정부지원사업 자료 분석

제공 자료에서 무엇을 알 수 있고 어떤 근거가 더 필요한지 정리한다. 사업계획의 약속, 문서의 실적 주장, 정적 구현 관측, 실제 실행·측정·승인을 구분하여 보고서 작성자가 사용할 근거를 만든다.

## 범위와 자료 위치

사용자가 지정한 과제·사업장·대상 기간·보고서 역할을 먼저 기록한다. 폴더명은 사용자의 식별 단서로 보존하되 승인된 과제명·연도·과제번호로 자동 확정하지 않는다. 보고 기준일이 없어도 목록·문서 구조·사업계획 분석은 진행하고, 기준일에 의존하는 진척·집행·성과 판단만 보류한다.

`doc-automation`과 함께 쓰는 경우 `docs/PLAN.md`, `docs/PRIVACY.md`를 먼저 읽는다. 원자료는 사용자가 정한 자료 폴더에서 읽고, 사본·추출·분석·해시는 저장소의 ignored `outputs/`·`analysis/`·`private/`에 보관한다. 재사용 스킬과 공개 예제에는 실제 사업명·원문·경로·화면·장비 식별값을 넣지 않는다.

새 실행의 목록과 사본은 다음 도구로 준비한다. `--group`은 사용자 폴더의 접두사이며 법적 서식 분류가 아니다. 입력과 출력이 겹치거나 실행 폴더가 이미 있으면 도구가 거부한다.

```sh
python <skill>/scripts/inventory_sources.py --source-root SOURCE \
  --workspace REPOSITORY --output REPOSITORY/outputs/NEW_RUN \
  --group 01_ --group 02_ --group 03_ --group 04_
```

입력은 실행하지 않고 SHA가 일치하는 사본에서 내용 분석을 수행한다. `.git`·의존성·캐시 제외와 민감 설정의 내용 분석 보류를 manifest에서 확인한다. Windows에서는 UTF-8 입출력을 사용한다. 해시 확인은 사실 확인이 아니다.

## 먼저 만들 분석계획

파일 수·유형, 문서/슬라이드/쪽/코드 범위와 읽기 상태를 확인한 뒤 실제 자료에 맞는 분석 순서를 적는다. 파일명이나 폴더 분류가 내용과 다르면 관측된 문서 역할을 별도로 기록한다. 대량 코드는 전 파일 목록과 해시를 만든 후 대상 모듈·문서·시험·로그의 연결을 중심으로 단계적으로 읽는다. 읽지 않은 파일을 정밀 분석 완료로 표시하지 않는다.

계획에는 각 작업의 질문, 우선 출처, 비교 대상, 근거 위치, 산출물, 완료 조건과 확인이 필요한 항목을 포함한다. 사업계획서의 범위·KPI·예산·일정을 기준 목록으로 만들고 발표자료, 개발 자료, 비용·실행 증빙과 대조하는 순서가 유용하다. 자료의 승인 상태에 따라 어느 문서를 기준으로 삼을지 근거를 남긴다.

형식별 읽기와 코퍼스 구분에는 [references/source-review.md](references/source-review.md)를 사용한다. 중간보고서의 항목별 질문은 [references/interim-analysis.md](references/interim-analysis.md)를 필요한 양식에 맞춰 사용한다.

공정별 설명을 보강하는 요청은 같은 참조의 공정·데이터·AI 대응을 만들고 현행 단절→데이터 소스→수집→AI 적용→개선 조치를 출처로 연결한다. KPI 산출근거 요청은 기준값의 계산 조건과 개선안까지 조사하며 계획 기준과 시점이 다른 실측 주장을 합치지 않는다.

## 근거를 정리하는 방법

자료별 원문·단위·적용 시점·locator를 남기고 추출값과 해석을 분리한다. [references/evidence-contract.md](references/evidence-contract.md)의 분석 원장에 다음 경계를 보존한다.

- 양식 지침, 전문가 관행, 이번 사업 사실, 구현 선택, 미확인·상충은 서로 다른 정보 유형이다.
- 계획·목표·원가산정은 실제 수행·측정·집행과 구별한다. 승인된 문서인지와 그 문서 안의 실적이 입증되었는지도 별개다.
- 파일 해시 대조, 원문 위치 대조, 사업 귀속 확인, 실제 실행·측정 확인, 승인 확인은 각각의 검토 상태로 기록한다.
- 코드·테스트·화면의 존재는 정적 관측이다. 문서가 설명하는 PASS나 실운영 주장은 연결된 원시 기록과 코드 버전·기간을 확인하기 전까지 보고 주장으로 보존한다.
- 동일 저장소 안의 다른 사업·공통 모듈·demo·synthetic·offline replay를 이번 과제의 실적에 합산하지 않는다. 이름이 비슷한 메뉴와 코드만으로 적용 완료를 판단하지 않는다.
- 자료 미제공을 0·미수행·미승인으로 바꾸지 않는다. 충돌은 양쪽 원문과 해석·해결 근거를 남기고 최신 파일이나 다수결로 자동 해결하지 않는다.

읽기·추출이 끝나면 보고서 항목별로 `supported`·`partial`·`missing`·`conflict`와 쓸 수 있는 사실·남은 확인을 표시한다. 이 상태는 작성 준비도이며 사업 성공·제출 적합 판정이 아니다.

## 완료와 다음 단계

완료 시 입력 목록과 원본 불변 여부, 실제 읽은 범위, 분석계획, 출처 원장, 상충·누락 목록, 보고서 항목 대응표를 연결한다. 상세 분석을 아직 하지 않았다면 사전조사와 정밀 분석 계획을 분명히 구분한다. 자료를 사용자 폴더로 옮기거나 원본을 고치지 않는다.

분석 중간물은 기존 공통 스키마를 임의 확장하지 않는다. 공통모델로 옮길 때는 해당 저장소의 `docs/DATA_MODEL.md`·`docs/BUSINESS_VALIDATION.md`·`schemas/project.schema.json`을 읽고 실제 필드와 검증기 지원 범위를 확인한다. 네이티브 locator와 원본 SHA를 보존한 원장을 JSON Pointer로 연결하는 방법은 evidence-contract 참조를 따른다.

사용자가 보고서 작성을 요청하면 `$gov-grants-smart-factory`와 `$hwpx-authoring`에 분석 결과를 넘긴다. 현재 양식 SHA·원본 범위·실제 지원 작성기를 다시 확인하며 과거 합성 예제의 기업·기능·수치·날짜를 실제 과제로 승격하지 않는다. 제출·서명·기관 승인이나 DB·운영 서비스 실행은 자료 분석 요청만으로 수행하지 않는다.
