# Project working rules

This project automates documents; the first domain is government-grant deliverables in HWPX. Read `docs/PLAN.md` and the relevant analysis or skill before changing the pipeline.

- Treat all user-supplied template/reference corpus folders as read-only. Keep private paths in local configuration, never public source. Record source SHA-256 and XML evidence locations. Work on project-local copies.
- Separate a template instruction, an observed expert convention, a project fact, an implementation choice and an unresolved issue. One exemplar project is not a universal standard.
- Read all sections in OPF spine order. Preserve inline text tails and keep table-cell text owned by its own paragraph. Numeric formatting IDs are local to each file.
- Preserve semantic objects and direct formatting when editing. Do not replace an enclosing paragraph's entire content when it contains a table, section control, image, formula, field, or header/footer.
- Generate no invented execution results, signatures, approvals or measurement evidence. Synthetic examples must be labeled inside the output document.
- A schema check, an existing ID, a picture, an OCR result, or a successful ZIP parse does not prove a fact or a final page layout.
- Native output QA must use the current generated bytes and report the actual Hancom version. Retain rendered pages and the review scope. Source defects and cross-version limitations must not become positive style rules.
- Keep the automation layers separate: package mechanics, source-specific profiles, shared facts, domain writing guidance and quality gates. Validate meaningful invariants and actual output behavior.

- Public source must contain no real-business-derived input, screenshot, signature, equipment identifier or personal absolute path. Keep private corpora, observations and historical QA outside Git; see `docs/PRIVACY.md`.

# 커밋 규칙

`project-hub`의 커밋 규칙과 검사 훅을 이관했다. 규격의 출처는 이 절이고, 판정은 `.githooks/commit-msg`가 한다. 규격 변경 시 이 절·훅·`scripts/hooks/commit-msg.test.sh`를 함께 갱신한다. 훅은 형식을 검사하며 변경 내용의 정확성이나 한국어 명사구의 의미까지 판정하지 않는다.

설치는 `bash scripts/hooks/install.sh`로 한다. 현재 저장소에만 `core.hooksPath=.githooks`를 설정하며, 새 checkout에서도 한 번 실행한다. 검사는 `bash scripts/hooks/commit-msg.test.sh`로 수행한다.

```text
<type>(<선택 scope>): <한국어 명사구 목적>

- <주요 변경을 한국어 명사구로>
- <주요 변경을 한국어 명사구로>
```

- 허용 type은 `feat`, `fix`, `test`, `docs`, `refactor`, `chore`, `merge`, `ops`, `db`, `release`.
- scope는 소문자 ASCII 문자나 숫자로 시작하고, 그다음은 소문자 ASCII 문자·숫자와 `.`, `_`, `/`, `-`만 쓴다.
- 제목은 100자 이내로 작성하고 제목 다음 줄은 비운다.
- 제목과 본문은 한국어 명사구로 적고 종결 어미 `다`나 종결 문장부호로 끝내지 않는다.
- 본문은 `- `로 시작하는 줄 2개 이상. 권고는 2~4개이며 넷을 넘으면 훅이 알리기만 하고 막지 않는다.
- `Co-Authored-By`, `Signed-off-by`, 생성 도구 표기를 넣지 않는다.
- `fixup!`·`squash!`·`amend!`와 Git 기본 `Merge …`·`Revert …` 메시지를 쓰지 않는다. 같은 규격으로 다시 쓴다.
- `merge` type은 부모가 둘 이상인 실제 병합 커밋에만 쓴다.
