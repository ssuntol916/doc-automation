# v2.0 산출물 초안 생성

공개 checkout에는 실제 사업 원문·참고 파생 입력·과거 native 검토 이력이 포함되지 않는다. 아래 과거 관측은 비공개 로컬 이력이며 새 출력 판정이 아니다. 현재 개선 반복은 중단 상태다. 원본 연결과 공개/비공개 경계는 [PRIVACY.md](PRIVACY.md)를 따른다.

`generate_project(input_path, output_dir, roles=None, template_root=None, *, style_profile=None, raster_metadata_profile=None)`는 19종 v2.0 원본 HWPX 양식에 공통 데이터 모델을 채운다. 반환값과 `output_dir/manifest.json`에는 입력·원본·출력 경로/SHA-256, 역할 코드, 경고, 제출 불가 및 네이티브 검토 대기 상태가 있다. 원본을 수정하거나 원본 폴더에 출력하지 않는다. 입력 오류가 있으면 출력 전에 중단한다.

전체 합성 예시는 다음 명령으로 재현한다.

```sh
.venv/bin/python scripts/generate_demo_suite.py
```

결과는 `generated/demo-suite/`의 HWPX 19개, 해당 DB 입력과 일치하는 검증용 Excel, manifest다. CLI의 `generate`도 같은 API를 사용한다. `roles`에는 canonical 코드 배열을 전달한다. 선택한 역할의 양식만 찾으므로 두 역할을 요청하면 그 두 원본만 있는 `template_root`를 사용할 수 있다. 기본 양식 경로는 `~/projects/gov-grants/_templates`이며 알려진 원본과 SHA가 다르면 프로필 재검토를 요구한다.

## 참고 편집 프로필 선택

`style_profile=None`은 기존 양식 보존 모드다. 참고 수준의 본문 구성·서식을 시험하려면 명시적으로 `style_profile="reference-v1"` 또는 CLI의 `--style-profile reference-v1`을 선택한다.

```sh
uv run doc-automation generate examples/demo-suite.project.json verification/reference-editorial-example --style-profile reference-v1
```

프로필은 `resources/style-upgrade/profiles/{역할}.json`이며 원본 양식 SHA가 일치해야 적용한다. 기존 글자·문단 정의를 수정하지 않고 필요한 정의를 파생하고, 선언된 본문 구역·열폭·셀 여백·역할별 서식만 변경한다. 표지와 본문을 분리하는 새 구역, 머리말·꼬리말·페이지 번호, 병합 셀과 그림의 연결은 별도 보존 대상이다. manifest의 `editorial_profile`에는 실제 읽은 프로필 경로/SHA/ID, 선택한 본문 위치, 변경 내역과 허용 변경 범위가 있다.

실제 사용한 프로필 원바이트는 출력 폴더의 `profiles/{역할}.json`에 고정한다. `profile_source.path`와 `sha256`은 이 사본을 가리키며, `origin_path`·`origin_sha256`에는 읽은 active 프로필을 기록한다. 적용 도중 active 바이트가 바뀌면 저장 전에 거부한다. 기존 출력 폴더에 다른 프로필 사본이 있으면 새 폴더를 요구한다. 후속 프로필 수정으로 과거 manifest의 경로가 다른 바이트를 가리키지 않도록 하는 장치이며 native 검토를 대신하지 않는다.

이 프로필의 상태는 `candidate_unvalidated`다. 프로필 적용이나 회귀 통과는 참고 수준 또는 95점 판정이 아니다. 현재 바이트의 한컴 출력·전체 원본 페이지와 `resources/style-upgrade/rubric.json`에 따른 편집 검토가 필요하다. 생성 시 `native_review_status=pending`, `submission_ready=false`를 유지한다.

참고 프로필의 본문 표현은 다음과 같다.

- AD2는 문서 수준 합성 고지를 표지에 유지하고 카드에는 짧은 자료 상태와 변경구분·비고를 표시한다. 원문 분류·원문 ID·필드별 확인 상태도 제공된 경우 보존한다.
- TD3는 각 필드를 이름/형식/필수/typed 기본값과 검증/출처의2문단으로, 버튼은 이름/동작/출처의1문단으로 구성한다. 긴 값은 자연스럽게 줄바꿈하며 필드·버튼·권한의 개별 출처를 보존한다. 기본값의0/false/null/빈 문자열/객체/목록과 자료형을 구별한다. 화면에 공유된 요구사항 전문은 본문의 R번호와 ‘부록. 화면 연결 요구사항’에서1번씩 대응한다. 화면 표준·메뉴의 설명은 제목과 별도 regular 문단이다.
- TD5는 각 행의 테이블명/ID를 유지한 단일 연속9열 표로 구성한다. 짧은 명세 행은 `pageBreak=TABLE`로 행 단위 분할을 요청한다. 좁은 PK/FK의 Y/N/?와 `?=원입력 미확인` 범례를 대응하며 정확한 key=null 등 원값·타입은 Cn 상세에 보존한다. NULL 허용은 불가/허용/미확인, 기본값·암호화·제약은 Cn에 표시한다. 한컴 행 분할 비교 실험 (로컬 자료: `verification/style-upgrade/experiments/td5-rowbreak-v1/native-findings.json`)은 CELL에서 잘린 같은 행이 TABLE에서 함께 시작한 근거다. 새 생성물·긴 행의 출력 품질은 별도로 native 검토해야 하며 TD3의 긴 카드에는 이 정책을 전용하지 않는다.
- PM4는 명시 연결1개를 비교표1행에 배치한다. 시작/대상 종류·ID·방향·관계·내용 검토/자료 상태·출처를 비교하며, 정확히 같은 값·타입의 연결 사유는 Q번호, 추가 명세는 N번호로1번만 작성한다. 각 행은 Q/N을 참조하고 `.meaning.json`·`.sources.json`은 원입력 trace와 실제 row/cell XPath를 대응한다. 입력에 없는 전이 관계·충족·수행을 추론하지 않는다.
- TD4의 조회 조건·등록 조건·계산 규칙은 해당 프로그램의 처리 명세 셀에, TI3의 버전은 해당 설명 옆에 표시한다. 매뉴얼의 대상 사용자가 null이면 별도의 ‘대상 사용자 미확인 설명’ 절에서 내용을 유지한다. PM1의 업무별 계획/실적 진도와 개별 상태·출처는 보고서 합계와 구분한다.
- 출처는 좁은 셀과 업무 본문에서 [S1] 등 문서 내 키로 참조한다. 문서 말미 ‘부록. 출처 대응표’에 `sources.title`·자료 ID·`verification_status`·종류·SHA·제공 경로·비고·원문 위치를 대응시키고, 동일 문서의 `.sources.json`에 정확한 source_ref 객체·source 객체·상태/분류 원문값 대응·입력과 HWPX SHA를 저장한다. 한국어로 표현한 상태·분류·관계의 원문 코드도 부록과 sidecar에 남긴다.

역할의 주 명세에서 사용하지 않은 개체 필드는 ‘부록. 항목별 보완 명세’에 읽을 수 있는 필드명과 값으로 배치한다. 이 보완 명세는 문자열·수치·논리값·null·빈 목록을 구별하며 원시 JSON을 출력하지 않는다. `.meaning.json`에는 역할별 입력 필드·leaf·선언한 주 명세 경로와 실제 보완 문단의 section/XPath·namespace를 남긴다. 주 명세 선언, ID가 나타난 문단 후보, leaf 개수, 보완 문단 일치만으로 의미 보존이나 편집 품질을 자동 통과시키지 않는다. 개별 `content_review_status`와 전체 `semantic_review_status`는 독립 의미 검토 전까지 pending이다.

임의 객체 기본값은 도메인 메타데이터와 구분한다. 기본값 안의 `status`·`source_refs`도 원래 key와 재귀적인 값/타입으로 표시하며 실제 상태 번역이나 출처 등록에 사용하지 않는다. 연결된 review는 의견·evidence/source 참조·대상 artifact SHA 등 모든 제공 상세를 ‘부록. 연결 검토 기록’과 sidecar에 보존한다. 이는 입력의 검토 주장을 보존하는 것이며 실제 승인·서명 검증은 아니다.

R(요구사항)·A(첨부)·D(자료) 등 부록의 짧은 소유키는 항목별 문단에 반복해 계속 쪽에서도 SHA·경로·제약의 소속을 식별하게 한다.240자 이하의 짧은 소유 문단만 keepLines를 적용하고 항목 전체나 부록 전체를 연결하지 않는다. 빈 연결 목록의 실제 부재/미수행 미판정 설명은 문서당1회로 구별한다. 최종 페이지의 실제 적합성은 새 native 출력에서 확인한다.

출처의 `source_id+locator`만 있는 항목은 같은 D자료 안에서 최대3개·160자 기준으로 한 소유문단에 묶는다. 각 S키와 locator 원문을 유지하고 sidecar의 source_ref별 `owner`가 같은 실제 문단을 가리킨다. 추가 메타데이터가 있는 참조는 개별 전체 표현을 유지한다. 마지막 두 항목 같은 특정 위치에 페이지 예외를 넣지 않는다.

CD1/TI1/TI4의 data/expected/actual은 임의 JSON 값이므로 도메인 필드와 분리한 typed literal로 작성한다. TI1/TI4의 nullable case_number/group_id/process_name은 개별 케이스 보완 명세에서 정확한 null을 유지하며, 프로젝트 참고 흐름을 실제 케이스 연결로 단정하지 않는다. PM4의 기능/비기능 모두 이행 상태와 결과물 연결은 T명세에 실제 owner를 기록한다.

아래의 세부 보존·기존 조판 관찰은 별도 언급이 없으면 기본 양식 보존 모드에 대한 설명이다. 예전 출력의 성공 여부를 새 편집 프로필로 승계하지 않는다.

## PNG를 저장할 한컴 버전 선택

Mac 한컴 Office HWP 12.30.0(build 6544)에 맞춰 새 PNG를 삽입하려면 `--raster-metadata-profile hancom-mac-12.30.0-png`를 명시한다. Python API는 같은 문자열을 `raster_metadata_profile`에 전달한다. 기본값 `None`은 기존 생성 동작을 유지하며, 업무 서식의 `--style-profile`과 별개다.

이 옵션은 PNG의 전체 래스터 `imgClip`·`imgDim` 좌표만 해당 버전에서 관찰한 60 HWPUNIT 격자로 작성한다. 원 PNG bytes·`orgSz`·표시 크기·배율·종횡비는 유지한다. 실제 DPI 메타데이터와 무관한 이 버전의 저장 동작을 재현한 구현 선택이며 HWPX 표준 규칙으로 일반화하지 않는다. 제공 BMP를 무손실 PNG로 변환한 삽입에도 적용되며 JPEG에는 적용하지 않는다. 다른 버전은 별도 현재 바이트 검증이 필요하다.

manifest의 `raster_metadata_profile`, 문서별 `inserted_picture_metadata`, 이미지별 `raster_metadata_profile`을 확인한다. 선언은 native 합격 증거가 아니다. 현재 한컴에서 14개 진단 그림의 새 API 삽입→저장→닫기→재열기→PDF 출력 후 엄격 비교 12항목이 통과했으며, 각 새 산출물은 자체 native 검토를 다시 수행한다. 로컬 증거는 `outputs/quality-loop/r04/png-profile-probe/native/`에 보관한다.

## 입력과 출력의 의미

- synthetic은 문서 안에 **검증용 합성 자료(제출용 아님)**을 표시하고 본문 항목의 자료·확인 상태를 구분한다. 계획 시험은 not_run/actual=null을 유지하고 실제 서명·수행·설치·승인 증거를 만들지 않는다.
- project는 **검토용 초안(제출 전 사실·증거 확인 필요)**로 표시한다. 제공된 실제 시험 판정/결과/일자/수행자, 설치값, 회의내용/합의, 변경 승인상태/회신을 미수행으로 덮어쓰지 않는다. 입력의 주장과 외부 사실 확인을 구별한다.
- reference_extraction은 새 사업의 문서로 생성하지 않는다. 기존 전문가의 기업 정보·서명·성과가 새 사업으로 승계되는 것을 막는다.
- 누락 사실은 미확인·자료 미제공으로 쓴다. 합성이라는 출처 분류도 수행 여부를 뜻하지 않는다. 회의일 null만으로 미개최를, 지원·작업 결과 null만으로 미수행을, 설치 결과 null만으로 미설치를 단정하지 않는다. 실제 값 0과 false는 보존한다. 서명 이미지를 생성하거나 담당자 이름을 날인으로 바꾸지 않는다.

지원하지 않는 제공 내용을 조용히 버리지 않는다. 제공된 PNG·JPEG·BMP는 선언한 MIME과 실제 Pillow 형식이 일치하는지 출력 전에 확인한다. 지원하는 의미 슬롯은 AD1/TD1 공정의 현행/개선 흐름도, TD2 시스템의 현행/목표 구성도, TD3 표준/기존/변경 화면, TD4 모듈 흐름도, CD1/TI1/TI4 시험 흐름도, TI3 매뉴얼 설명 그림이다. 그림은 해당 개체 ID·슬롯·캡션·출처·확인상태와 연결하며 원본 비율을 유지하고 자르지 않는다. 합성 첨부에는 ‘합성 시안·실제 실행화면 아님’을 표시한다.

AD1 회사 소개에 조직도를 제공하려면 `project.organization_chart_attachment_ids`에 PNG/JPEG/BMP 첨부 ID 목록을 연결한다. 사업/도입기업의 단일 owner에 귀속하며 회사 소개 뒤·전체 업무 흐름도 앞에 넣는다. 공정 흐름도 슬롯을 조직도에 재사용하지 않는다. ID/SHA/MIME·실제/참고/합성 상태·제공 캡션을 검증하며, AD1을 생성하지 않는 선택에서 이 슬롯이 제공되면 조용히 버리지 않고 거부한다. 입력에 없는 실제 조직·임명·승인을 추론하지 않는다.

과거 참고 화면·사진의 비교용 재현은 [전용 인용 계약](REFERENCE_QUOTATIONS.md)을 따른다. 등록된6개 원문 소유 인스턴스만 source SHA/XML/bitmap/pixels/역사적 소유자를 대조해 전용 필드로 연결한다. 선택한 `detail_regions`는 전체 그림을 먼저 보존하고 원본 픽셀 영역의 추가 보기를 만든다. 이 경로에는 명시한 `hancom-mac-12.30.0-png`가 필요하며, 각 보기의 고지·현재 ID·Q/D키·원본 좌표를 유지한다. 본문에 새 실행 결과나 증적을 생성하지 않는다. 실제 출력 가독성은 별도 검토한다.

AD1의 실제 그림 경로는 현행 공정 `as_is_attachment_ids`와 현행 시스템 `as_is_diagram_ids`다. TD1은 공정의 현행/개선 비교를, TD2는 시스템의 현행/목표 비교를 사용한다. 개수가 같다는 검사만으로 역할에 맞는 그림이 삽입되었다고 판정하지 않으며, 정확한 entity/slot/attachment 조합과 실제 삽입 binary를 대조한다.

PNG/JPEG는 입력 바이트를 그대로 삽입한다. BMP는 원본을 변경하지 않고 무손실 PNG로 변환한다. manifest의 `image_bindings`는 원본 SHA와 삽입 SHA, 변환 여부, 개체/첨부 ID, 의미 슬롯, 캡션·인쇄 크기·크롭 없음 기록을 남긴다. 그림 존재는 실제 구현·수행·승인의 증거가 아니며, 실제 시험 증거와 변경 승인 증거는 제공된 ID로 참조한다. 입력으로 연결된 물리DB Excel 자체의 삽입은 아직 지원하지 않으므로 해당 배열에 값이 있으면 출력 전에 거절한다. PM1의 여러 보고기간도 별도 출력 선택을 요구한다.

참고 프로필의 그림 캡션은 label·소속 ID·짧은 제공 caption·[An] 첨부키를 사용하며 중복 합성 고지를 덧붙이지 않는다. 긴 제공 caption은 축약·잘라내지 않고 ‘부록. 첨부 그림 대응표’에 원문 그대로 표시한다. 정확한 attachment ID·SHA·제공 경로·용도·상태·notes와 사용 슬롯도 이 부록과 `.sources.json`의 `attachments`에 대응한다. 문서 본문에서 메타데이터를 줄였다는 이유로 원문 입력을 부속 JSON에만 숨기지 않는다. 그림·캡션 문단은 삽입 전부터 명시 registry로 연결하고 실제 프로필의 caption 역할을 적용한다.

본문 셀은 논리 cellAddr로 선택한다. 상세 카드의 표를 감싼 문단을 복제하여 표 구조·열폭·셀 여백·문단 서식을 재사용한다. 목록은 원본 행을 반복하고 rowCnt/논리행 주소/표높이를 갱신하며 머리행 반복을 설정한다. 장문·55컬럼 stress 입력도 문장/행을 생략하거나 축약하지 않는다. 실제 페이지 흐름은 한글에서 확인한다.

AD2 stress의 긴 두 요구사항은 XML에 마지막 marker·제약·담당자·출처·비고가 있었지만 기존 pageBreak=NONE 카드의 화면/인쇄 하단에서 누락됐다. AD2는 기존 floating 위치·geometry를 유지하고 CELL 분할을 요청하며, 계속쪽에서도 요구 대상을 읽도록 첫 두 행(시스템/영역 및 요구 ID/이름)을 반복한다. 본문을 축약하거나 폰트를 줄이지 않고 첫 section/번호/필드 제어를 보존한다. 실제 계속쪽·최종 marker와 아래 셀의 완전성은 새 native 출력에서 확인해야 한다.

AD2 원본의 ‘기능/비기능 분리’ 지침과 두 분류 목차를 따라 제공된 kind로만 그룹을 나눈다. null은 비기능으로 추정하지 않고 별도 ‘유형 미확인 요구사항’ 그룹에 둔다. 비어 있는 그룹은 생략하고 남은 그룹에 연속 번호를 부여한다. 목차는 그룹 제목과 하위 요구 ID/이름을 쓰되 첫 자식 항목에 제목과 줄바꿈을 함께 두어 카드당 측정 항목 하나와 한 논리 목차 문단을 유지한다. 원래 ID·입력 객체·분류값·카드의 유형 셀과 geometry는 바꾸지 않는다. 이전 선형 AD2 목차는 현재 프로필과 다르므로 재생성·새 native 출력이 필요하다.

지침 제거는 `※ 작성 방법`으로 명시된 원본 끝 영역을 선택한다. 파란색이라는 이유만으로 텍스트를 삭제하지 않는다. 입력 글자의 원본 회색/파란색은 가독성을 위해 검정 charPr 복제로 바꾸되 폰트·크기·강조·간격과 원본 정의를 보존한다. 원본 metadata의 예전 작성자/다른 문서 제목은 제거한다. 원본의 오래된 머리말 연도와 잘못된 CD2/TI5 지침은 새 사실로 남기지 않는다.

기업명 치환은 section0 표지의 직계 문단에 한정한다. 본문 변경요청서의 ‘도입기업명/공급기업명’ 같은 고정 라벨을 실제 값으로 바꾸지 않는다. 머리말은 header 제어 안의 해당 문단에서 입력 사업명·사업연도와 현재 문서 역할을 반영한다. 원본에 잘못 남은 ‘일정계획서’ 제목을 연도만 바꿔 승계하지 않는다.

`reference-v1`의 표지 사업명에는 제공된 사업연도를 함께 표시한다. 제공된 사업명이 이미 `YYYY년` 또는 `YYYY년도`로 시작하면 그 문구를 그대로 유지하며, 연도를 추론하거나 작성일로 대신하지 않는다. 사업명 문단의 줄바꿈은 별도 선언한 프로필 범위에 한해 변경하고, 글자 크기·문구·다른 표지 속성은 유지한다. 표지의 실제 줄 수·상자 높이·후속 문단 위치는 현재 한컴 출력으로 확인한다.

표지 고지는 원래 존재하는 9~11pt의 빈 직계 문단에 채운다. 큰 기업명 문단에 줄을 추가하지 않고 표지 여백·문단 배치·구역 속성을 보존한다. 네이티브 최초 출력에서 고지 한 줄의 추가가 공급기업명만 다음 쪽으로 밀어낸 문제가 확인되어 이 방식을 사용한다. 좁은 비고 열의 긴 notes/JSON locator와 장황한 구분명도 원본 열폭·폰트를 줄이지 않고 넓은 근거 문단으로 옮긴다. 이 선택은 현재 v2 양식의 가독성 개선이며 모든 양식의 고정 규칙이 아니다.

AD1 최초 출력의 ‘네트워/크’ 쪽 경계 분리 대응으로, `_narrative`가 만든 제목에만 `hh:breakSetting keepWithNext="1"`, 240자 이하의 짧은 일반 본문 문단에만 `keepLines="1"`을 사용한다. 원본 paraPr는 그대로 두고 해당 속성만 바꾼 local 파생 정의를 추가한다. 본문의 keepWithNext는 원본 값(현재 7프로필 모두0)을 유지한다. 줄바꿈으로 나눈 문단은 각자 판단하며 연속 문단 전체를 묶지 않는다. 긴 문단·AD2/TD5 등 상세 표의 스트레스 문단에는 이 정책을 적용하지 않는다. 글자 크기·간격·표 기하를 바꾸지 않으며 실제 효과는 후속 한글 출력으로 확인해야 한다. 영향 역할은 AD1/TD1/TD2/TI2/TI3/OS1/OS2다.

TD5 최초 후속 출력에서는 좁은 비고의 반복된 암호화/기본값 설명이 한 글자씩 길게 세워져 행이 쪽 경계에서 갈라졌다. 이를 C1부터의 문서 내 고유 키로 바꾸고 표 뒤의 ‘컬럼별 제약·암호화·기본값·근거’ [C1] 상세로 전체 입력을 옮긴다. 비고의 대괄호를 빼 C10도 세 글자로 제한한다. 기본값0/false/null과 암호화 미확인/미적용을 구별하고 field_states 및 FK/기준명세 근거도 있는 그대로 보존한다. stress는 3테이블·74컬럼 전체의 키/상세 대응을 검사한다. 원본 열폭·폰트를 줄이거나 컬럼 행을 생략하지 않으며, 최종 페이지 효과는 현재 바이트의 한글 출력에서 확인한다.

TD5의 공통 고지와 per-card metadata를 표 앞에 삽입하면 첫 설명·복합 UNIQUE가 TOC 주변에 놓이고 다음 테이블의 설명이 앞 표 뒤에 보일 수 있었다. TD5에 한해 기본/per-card `_body_notice`를 쓰지 않고, 모든 테이블 목록 뒤에 공통 합성/검토용 고지·과제·전체 테이블ID·부속 Excel 안내를 한 번 배치한다. 이어 ‘2. 테이블별 설명·제약·근거’의 [Tn]에 같은 ID·이름으로 각 테이블의 description/notes/source_refs를 보존하고 ‘3. 컬럼별…’ Cn 상세를 뒤에 둔다. TOC 항목 영역과 본문 metadata의 소유 문단·순서를 구별하며, 기존 표 열폭·글꼴·쪽번호/section 제어는 바꾸지 않는다. TOC 갱신 자체의 본문 보존과 실제 최종 페이지 배치는 별도 검증한다.

TD5 stress의 Cn 제목 고립과 짧은 본문의 쪽 경계 단어 분리를 줄이도록, 표 뒤 append 본문에서 240자 이하 문단만 keepLines를 요청하고 절 제목·[Tn]/[Cn] 제목에 keepWithNext를 요청한다. 하나의 [Tn] 또는 [Cn] entry가 최대 6문단, 각 문단 240자 이하, 합계 720자 이하일 때만 그 entry 안의 문단을 연결하고 마지막 문단의 keepWithNext를 0으로 둔다. 범위를 넘으면 제목 연결/짧은 문단 보호만 유지하여 자연 분할한다. 이는 TD5의 기존 9~11pt 본문과 원본 폭에 한정한 배치 선택이며 여러 entry·테이블 전체를 연결하는 규칙이 아니다. 기존 paraPr를 수정하지 않고 keep 플래그만 파생하며 글꼴·크기·간격을 줄이지 않는다. 최종 출처만 별도 꼬리쪽에 남는 현상을 줄이는 효과는 실제 새 출력에서 확인한다. 머리행 부재로 보고됐던 관찰은 단독 원본 PNG 재확인에서 오독으로 정정됐으며 metadata/keep가 머리행을 고쳤다고 결론내리지 않는다.

TD3의 최초 native 검토에서 원본의 분할 금지 카드가 한 쪽보다 커져 하단의 권한·프로그램·출처 텍스트가 PDF에서 누락되고, 뒤의 4절이 두 카드 사이에 나타났다. 한컴 도움말의 글자처럼 취급 제한과 격리 실험을 반영해 해당 역할에만 pageBreak=CELL, pos.treatAsChar=0을 사용하며 flowWithText와 기존 geometry는 유지한다. R3C1/R4C1의 inline newline을 실제 문단으로 나누고 240자 이하의 짧은 문단만 keepLines, 콜론으로 끝나는 label 및 연결 요구사항의 정확한 입력 ID/이름 제목만 keepWithNext를 요청한다. 3절 제목은 새 쪽에서 시작하여 기존 합성/검토용 고지 세 문단과 첫 카드 앞까지만 연결하고 전체 카드·연속 본문을 묶지 않는다. 머리행 반복·모든 카드 뒤 4절 쪽 나눔을 유지하며 현재 생성 바이트에서 다시 native 검증해야 한다. TD4는 별도 구역/복제 제어가 원인이 아니라 마지막 작성지침 문단이 가진 두 번째 newNum(PAGE,1)이 빈 문단에 남은 문제로 확인되었다. 그 원본 문구와 제어 범위를 특정해 제거하며, 앞의 본문 시작 PAGE=1 및 section/쪽서식은 유지한다. 이 조치는 새 후보의 native 재출력으로 확인해야 한다.

CD1·TI4도 원본의 마지막 결함관리 작성지침이 가진 별도 PAGE=1 제어를 텍스트만 지우고 남겨 본문 인쇄쪽 1이 반복됐다. 세 역할의 정확한 지침 문구·단일 PAGE=1·다른 범위 제어 없음이 모두 확인되는 경우에만 그 지침 문단을 제거하며 정상 본문 시작 제어는 유지한다. CD1의 3374 HWP 단위 완료일자 칸에는 날짜 또는 짧은 미확인만 두고, 조치 칸의 [Dn]이 가리키는 넓은 ‘결함별 검증 상태·근거 상세’에 원래의 resolution_status/검증 증거/확인자 자료 고지와 입력 담당자·비고·출처를 보존한다. 검증 상태를 날짜나 실제 서명으로 바꾸지 않으며 새 PDF에서 줄바꿈·쪽번호를 다시 확인해야 한다.

OS1/TD3/TD4/TD5는 원본의 pageNum/newNum(PAGE,1) 쌍이 첫 본문의 명시적 쪽 나눔보다 앞에 있어 TOC 쪽에서 번호1을 소모했다. 각 확정 프로필의 실제 첫 본문 문단으로 그 쌍을 옮기고 OS1의 동일한 두 쌍은 하나로 통합한다. 본문 경계·원본 쌍 개수·PAGE=1이 예상과 다르면 생성을 거부하며 section·표지 숨김·다른 제어는 옮기지 않는다. 실제 첫 본문 인쇄1과 이후 연속번호는 새 native 출력에서 확인해야 한다. 기존 TOC 부근의 별도 본문 고지 배치는 이 번호 이동으로 자동 변경하지 않는다.

PM4 기능 비고2564/비기능 비고4624 HWP 단위에 전체 출처·변경 근거가 들어가 세로 분절되던 문제는 짧은 T키와 전폭 추적 상세로 대응한다. 기능/비기능/null 모두 같은 추적 상세를 사용하며 각 도메인의 직접 requirement_ids와 requirements↔도메인의 명시 trace 양쪽을 합쳐 화면·프로그램·DB·시험단계별 ID를 보존한다. 원문 trace 객체는 해당 요구사항을 source 또는 target으로 직접 가리킨 것만 방향·관계·notes·status·content_review_status·source_refs까지 그대로 표시한다. 전이 연결을 추론하거나 관련 없는 개체의 metadata 전체를 인쇄하지 않는다. 원문 분류·요구사항 notes/출처 및 기존 기능·변경 근거도 유지한다. 원본 열폭·폰트와 모든 다른 연결 ID 열은 유지한다. PM3 요청자3810/요청일2982/회신일3203 HWP 단위의 미제공 기본문구만 짧게 쓰며, 실제 입력 이름·날짜·공문번호·회신내용은 길이로 자르지 않는다. 이름이 null이어도 제공된 소속·직책·연락처·검토상태·출처는 상세 비고의 요청자 객체에 남긴다. 날짜 미상만으로 ‘미요청’ 또는 미승인을 추정하지 않는다.

PM4 v5 실제 출력에서 짧은 T2 제목과 raw trace의 ‘합성’이 쪽 경계에서 나뉘었다. 해당 전폭 본문의 240자 이하 문단에 keepLines를, Tn/절 제목에만 keepWithNext를 요청한다. raw trace는 글자를 재배열하거나 JSON을 쪼개지 않고 한 문단 그대로 보존하며, 그 한 문단이 720자 이하일 때만 keepLines를 요청한다. 이는 현 PM4 원본의 10pt·전폭에서 관찰된 424~434자(6~7줄) 기록을 위한 유한한 배치 선택이다. 더 큰 trace는 원문 전체를 보존하고 자연 분할하며 여러 trace·요구사항 전체를 연결하지 않는다. 폰트·크기·폭·기존 정의는 유지하고 keep 정의만 파생한다. 이전 v5 시각 실패는 보존하며 새 현재 바이트에서 native 재출력·전체 페이지 검토를 요구한다.

PM3 실제 출력에서는 ‘변경요청서’ 제목만 대장 아래에 남고 바로 다음의 상세 표가 다음 쪽으로 옮겨졌다. 현 원본의 제목과 표 anchor에는 강제 쪽 나눔이 없지만 표의 NONE 분할 정책 때문에 남은 공간에 표가 맞지 않으면 표만 넘어갈 수 있었다. 해당 원본 제목 문단만 새 쪽에서 시작하고 keepLines/keepWithNext를 요청한다. 표 anchor의 keep는 0이며 원본 표 geometry·분할·floating 속성·내용·글꼴·크기·폭은 유지한다. 전체 표나 여러 변경요청을 한쪽에 묶는 정책이 아니며 현재 생성 바이트를 새 native 출력으로 확인해야 한다.

TD3 필드의 required는 true=필수, false=선택, null=필수 여부 미확인이다. null을 선택으로 확정하지 않는다. 기본값 null은 ‘기본값 미확인(null)’으로 표시하고, 제공된 0/false/문자열/빈 문자열/객체/배열은 JSON literal로 표시하여 타입과 값을 보존한다. 빈 문자열 `""`을 숫자0이나 미확인으로 바꾸지 않으며 null을 ‘기본값 없음’으로 확정하지 않는다. 화면 notes와 feature_ids는 넓은 주요 체크·검토 셀에 전체 표시한다. 이 프로필은 화면 상위 source_refs를 인쇄하며 fields/buttons/permissions의 개별 source_refs를 각각 인쇄하지 않는다. 세부 출처의 정확한 확인은 SHA로 연결된 원입력 JSON의 해당 객체를 별도 검토해야 하고, 이 한계는 생성 manifest warning에도 남긴다.

TD3 v2.0 원본의 ID 작성 지침은 ‘시스템명 3자리 + 문서명 3자리 + 일련번호 3자리’다. 제공 화면 ID가 이 literal 형식과 다르면 manifest에 원본 지침과의 차이를 경고하고 ID 자체는 보존한다. 합성 DEMO 접두어도 임의로 MES로 바꾸지 않는다. 이 특정 원본의 지침 차이는 실제 사업의 현행 명명 규칙 위반 판정과 다르며 추가 확인이 필요하다. 경고는 HWPX 내용을 바꾸지 않는다.

요구사항 kind는 functional/nonfunctional/null을 각각 기능/비기능/구분 미확인으로 구분한다. PM4의 미분류 요구사항은 두 확정 분류 표에 넣지 않고 별도 전폭 본문에 설명·세부내용·제약·담당자·확인상태·원문구분·notes·출처·결과물·검토·연결 ID와 해당 요구사항을 참조하는 양방향 trace 원문을 보존한다. 명시적으로 분류된 행의 기존 두 표 흐름은 유지한다. PM1 위험/이슈 kind=null도 미확인으로 표시한다. report_kind의 monthly/weekly/interim/completion/other/null을 그대로 구별하며 월간 양식 사용만으로 월간보고로 재분류하지 않는다. completion은 보고 유형이며 실제 완료나 수행을 입증하지 않는다. TD5 precision이 있고 scale=null이면 `(정밀도,미확인)`으로 쓰고 상세의 raw `scale=null`도 보존한다. 명시된 scale=0과 scale=3은 그대로 표시한다.

실제 project 입력에서는 미제공 실행값을 미수행 사실로 확정하지 않는다. TD2는 설치 상태·실제 사양·수량·일자·검증 결과·증거와 제공된 초기데이터 전환 값을 입력대로 표시한다. 명시적 planned 상태이며 모든 실제값/증거가 없는 합성 설치 계획만 기존 미수행 계획 표시를 유지한다. TI1/TI4에 케이스가 없으면 project에서는 실행 여부 미확인으로 쓰고, OS2의 빈 조치/지원 결과도 실제 수행 자료 미제공·미확인으로 쓴다. PM2 날짜 null은 개최일 미확인으로 표시하며 제공된 회의내용·합의·참석자를 지우지 않는다. 합성 입력도 실제 회의내용이 있으면 날짜만으로 개최 미수행을 단정하지 않는다.

TI2/OS1의 project 목차는 본문과 대응하는 중립 절 제목을 쓰며 미설치/미수행을 붙이지 않는다. OS2 project의 목차에 합성 집계/실제 운영 아님을 붙이지 않고, 등록 로그 부재도 고정 문구로 주장하지 않는다. 제공 원시행·집계는 보존하고 실제 자료의 진위와 충분성은 별도 검토한다. TD3 project 또는 연결 검토 기록이 있는 합성 화면은 ‘승인 없음/공통 표준 실제 승인 미수행’을 생성하지 않는다. 캡처 이미지 미삽입과 승인 상태를 구분하고, 입력 approved·검토자·일자는 보존하되 실제 승인 범위와 근거의 확인은 남긴다.

한글의 section 첫 문단에 secPr이 남아야 한다. 그 앞에 알림 문단을 삽입하지 않는다. 복제 문단에 문서범위 제어를 중복하지 않으며 빈 ctrl/run도 남기지 않는다. 표지에 고지가 있고 본문에도 검토 상태를 표시한다.

## 목차·DB 부속·검증

샘플 ID와 샘플 쪽수를 실제 값처럼 두지 않는다. 초기 목차는 본문 구조/실제 ID를 나열하고 페이지 번호는 네이티브 출력 후 확인 대기다. TD3는 네 절을 유지한 채 제3절 아래 화면 ID를 둔다. 최종 쪽수는 별도 네이티브 출력 후 갱신/재출력으로 확인해야 한다.

검증용 DB Excel은 `generate --companion-verification REPORT.json`으로 보고서를 명시한 경우에만 입력/출력 SHA와 현재 DB 필드의 canonical JSON을 대조해 재사용한다. 보고서를 생략하면 로컬 outputs 폴더를 자동 탐색하지 않고 부속 미제공으로 남긴다. stress의 추가 테이블/컬럼에는 기존 2테이블·19컬럼 파일을 붙이지 않는다. 불일치 시 본문에 일치 확인된 부속 미제공을 쓰고 manifest에 부속을 기록하지 않는다. 합성 Excel은 실제 구현된 물리DB export 증거가 아니다.

`tests/test_renderers.py`는 19종 원본 해시·서식/페이지 속성, 합성 표지, 지침 제거, 모든 반복 내용, 구체 TD3 규칙, 실제값 보존, 선택 양식 경로, 출력 전 거절, stress 전체 문단·행·잘못된 부속 방지를 검사한다. 원본 v2 양식이 설치되지 않은 환경에서는 해당 통합 검사를 명시적으로 skip한다.

ZIP/XML·참조 검사는 실제 한글 열기·PDF 출력·전체 페이지 시각 검토를 대신하지 않는다. 생성 결과의 native_review_status는 pending이고 submission_ready는 false다. [품질근거 계약](../schemas/quality-review.schema.json)과 현재 파일 SHA에 연결된 별도 검토를 거쳐야 한다. 원본 PDF나 이전 출력의 검토를 새 출력으로 승계하지 않는다.
