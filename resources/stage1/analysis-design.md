# 1단계: 분석·설계 산출물 양식 8종의 구조와 작성 지침

검토일: 2026-10-24. 범위는 `_templates` 안의 `SF-AD1~AD3`, `SF-TD1~TD5` **양식 원본만**이다. 참고자료와의 비교는 포함하지 않았다. 원본은 수정하지 않았으며 파일 경로와 SHA-256은 근거 목록 (로컬 상세근거: `analysis/stage1/analysis-design-evidence/manifest.json`)에 기록했다. 파일명의 양식 버전은 모두 `V2.0`; 사업 연도나 법령·공고의 현재 효력을 의미하지 않는다. 문서코드는 파일명에서 읽은 식별자이며 내부 문서 식별 체계와 별도로 관리해야 한다.

## 근거를 읽는 방법

- `s0`, `s1`은 각각 `Contents/section0.xml`, `Contents/section1.xml`이다. `p[n]`은 해당 section의 직접 자식 문단으로 **1부터** 센다. 예: `s1 p[9]` = `/hs:sec/p[9]`.
- `Tn`은 **section 안에서** XML 순서로 센 표 번호다. `RrCc`는 표의 `cellAddr.rowAddr/colAddr`를 그대로 사용한 **0부터** 시작하는 논리 좌표다. XML 행에서 몇 번째 셀인지를 뜻하지 않는다. 병합으로 셀 수가 달라질 때 특히 중요하다.
- 각 문서의 JSON (로컬 상세근거: `analysis/stage1/analysis-design-evidence`)은 문단·run·표·셀의 정확한 XPath, 속성, 크기, 병합, 문단/글자모양 참조, 머리말, 페이지 설정을 담는다. 동일 이름의 `.txt`는 사람이 읽는 요약이다. 원문 작성 지침은 `analysis-design-rules.json`에도 문단별로 저장했다.
- 추출기는 문단에서 자식 `tbl/header/footer/p`로 들어가지 않는다. 표 안의 문단은 각 셀에서 한 번만 읽는다. 따라서 표를 포함한 상위 문단의 텍스트와 셀 텍스트를 중복 합산하지 않는다. 원본의 공백·오타는 원문 근거에 유지한다.
- 아래 **양식 지침**은 해당 원본의 명시된 작성 방식이다. 법령·기관의 현재 의무로 확정하지 않는다. **생성 권고**는 품질을 위한 구현 판단이다. **보류**는 원본만으로 확정하지 못한 사항이다.

## 공통 구조와 스타일

8종 모두 표지에 `도입기업명`, `202 . .` 형태의 날짜 자리표시자, `공급기업명`이 있다. 표지의 1×1 표에는 `스마트공장 보급·확산사업`과 해당 문서 제목이 두 문단으로 들어간다. **표지 바깥 문단과 제목 표는 같은 문단에 함께 놓일 수 있으므로 통째로 텍스트를 치환하면 문서 제목 표가 유실될 수 있다.**

- 모든 section의 페이지 원시 속성은 `width=59528`, `height=84188`, `landscape=WIDELY`, `gutterType=LEFT_ONLY`이다. `pagePr/margin`은 `left=right=5102`, `top=bottom=header=footer=4252`, `gutter=0`. 열거형 이름만 보고 가로 방향이라고 단정하지 말고 원시 설정을 유지한다.
- 표지 제목 표는 `width=46934`, `height=9069`, `treatAsChar=1`, `pageBreak=CELL`, `repeatHeader=1`, 안쪽 여백 `141`이다. 실제 값은 한글 문서 단위 그대로이며 변환 과정에서 반올림하지 않는다.
- 실제 텍스트 run에 쓰인 한글 글꼴은 모두 **바탕체**다. header에는 맑은 고딕, 굴림, 한컴바탕 등의 다른 정의도 있으나 정의가 존재한다는 이유로 본문용 글꼴로 선택하면 안 된다. 글꼴은 `isEmbedded=0`이다.
- 표지에서 실제 사용한 글자 크기는 20/22/24/26/28pt 등이고, 목차는 대체로 12pt이다. 본문 표 라벨은 대체로 굵은 10pt, 입력부는 10pt, 작성방법 제목은 굵은 11pt, 작성 지침은 파란색(`#0000FF`) 10pt가 주로 쓰인다. 같은 의미의 글자모양 ID가 문서마다 다르므로 ID 숫자를 전역 상수로 사용하지 않는다.
- 파란색은 작성 지침뿐 아니라 일부 목차/항목 자리표시자에도 쓰인다. 색만으로 삭제 대상을 정할 수 없다. 원본의 `※ 작성 방법` 시작 위치와 문서별 블록 경계를 명시해 구분한다.
- AD1/AD2/TD1/TD2는 2개 section, AD3/TD3/TD4/TD5는 1개 section이다. 각 파일의 본문 section에는 아래 가운데 `pageNum pos=BOTTOM_CENTER formatType=DIGIT sideChar=-`가 있다. 일반 footer 텍스트 요소가 없어도 쪽번호 제어는 별도로 남는다.
- AD1/TD1/TD2 본문 골격은 **1×1 표 안의 제목 목록**이다. 이를 문서 내용 자체가 완료된 것으로 세면 안 된다. 실제 회사 설명·흐름도·설계 내용을 각 제목 아래 확장해야 한다.
- 모든 원본 표에 `repeatHeader=1`이 있어도 모든 셀의 `header` 속성은 0이다. 실제 여러 페이지 표 머리행 반복 여부는 한글 렌더링으로 확인해야 한다. `repeatHeader=1` 단독으로 반복 성공을 주장하지 않는다.
- 모든 본문 표는 `treatAsChar=0`, `flowWithText=1`, `allowOverlap=0`인 부유 표다. 원본의 위치 offset을 포함하여 블록 복제 시 보존하고, 내용 증가 후 겹침·잘림을 확인해야 한다.
- 이 8개 원본에서 중첩 표는 발견되지 않았다. 구조 검사에서는 표의 논리 격자 전체가 빠짐·중복 없이 채워지는지와 span 경계가 행·열 수를 넘지 않는지 별도로 확인했다.

## SF-AD1 현행업무분석서

근거: SF-AD1.json (로컬 상세근거: `analysis/stage1/analysis-design-evidence/SF-AD1.json`), 텍스트 (로컬 상세근거: `analysis/stage1/analysis-design-evidence/SF-AD1.txt`).

**용도와 구성.** 도입기업의 현재 업무 및 시스템을 조사하여 문제점과 개선 방향을 기록한다. 표지/목차는 s0, 본문 골격과 작성 지침은 s1에 있다. s0 p[29]~p[41] 목차에 두 대단원과 세부항목, 예시 쪽수가 있다. 본문 표는 s1 p[1]/run[2]/tbl[1], 1×1, `pageBreak=CELL`, 크기 `47626×25199`. 유일한 셀 R0C0에 다음 골격이 12개 문단으로 들어간다.

1. 업무 현황 분석 결과: 도입기업 소개, 전체 업무 흐름도, 주요 공정별 업무 흐름도, 현행 업무 분석 결과.
2. 기존시스템에 대한 현황 분석 결과: 시스템/HW/SW/NW 구성도, 메뉴 구조도, 기존 시스템 분석 결과.

**양식 지침.** s1 p[4], p[6], p[8]은 운영 중인 업무·시스템의 조사 및 두 갈래 목차 구분, 문제점·개선사항 제시를 요구한다. p[9] 기업 소개에는 원문의 `연역`(통상 연혁 의미로 해석되나 원문 보존), 주생산품, 조직도. p[10] 전체 업무 및 부서 연결과 업무영역 구분. p[11] 사업 관련 공정별 세부 흐름과 업무 세부내용 **2단계** 구분. p[12] 수작업·기능 노후화 등 현행 문제/이슈. p[13] 업무 문제점과 개선사항. p[15] 전체 정보화 현황 문제점·개선사항. p[16] 전체 시스템/HW/SW/NW 구성을 제시하고, 기존 시스템이 없을 때도 PC·파일서버·홈페이지·네트워크를 기술한다. p[17] 현행 기능을 확인할 수 있는 상세 메뉴 구조. p[18] 시스템 문제점, 개선사항, 본 사업과의 관계, 기존 시스템/장비 활용 방안.

**필수 입력과 반복.** 기업 기본정보, 현재 조직·업무·공정, 현행 장비/시스템/메뉴, 사실에 근거한 문제점과 개선 연결 정보가 필요하다. 공정별 흐름도와 시스템 구성 세부 항목은 대상 수에 따라 반복·확장한다. 현행 시스템이 없다는 이유로 2단원 전체를 무조건 삭제하지 않는다.

**머리말·보류.** s0 p[21]/run[1]/ctrl[1]/header[1]은 빈 머리말이며 과거 연도 문자열은 없다. 표 안에 제목과 그림이 늘어날 때 장기 표의 쪽분할, 실제 목차 쪽수, 그림 설명 위치는 XML만으로 검증되지 않았다. 예시 목차에서 `시스템 구성도 6` 등이 실제 본문 쪽수로 확정된 것은 아니다.

## SF-AD2 요구사항정의서

근거: SF-AD2.json (로컬 상세근거: `analysis/stage1/analysis-design-evidence/SF-AD2.json`), 텍스트 (로컬 상세근거: `analysis/stage1/analysis-design-evidence/SF-AD2.txt`).

**용도와 구성.** 승인 사업범위를 기준으로 협의된 요구사항 세부요건·제약사항을 기능/비기능으로 나누어 명확히 정의한다. s0 p[29]~p[45]는 두 유형별 요구사항명과 쪽수 자리표시자 목차다. 본문 반복표는 s1 p[1]/run[3]/tbl[1], **8행×4열**, `pageBreak=NONE`, 크기 `49034×27930`. 표 전체를 요구사항 1건의 반복 단위로 다룬다.

| 논리 행 | 라벨/입력 좌표 | 병합 |

| R0 | C0 시스템명 / C1 값, C2 업무영역명 / C3 값 | 없음 |

R0 열너비는 `8013/16220/6881/17920`, 입력부 병합 폭 `41021`, 기본 안쪽 여백은 `283`이다. 라벨은 글자모양 31(바탕체 10pt 굵게)·문단모양 3, 일반 빈 입력부는 글자모양 3(바탕체 10pt)·문단모양 0을 쓴다. 서명 안내의 회색 run도 별도 보존·대체 대상을 구분한다.

**양식 지침 전수.** s1 p[4]: 착수계·사업계획서·SW개발비 사업비 산출내역서의 범위에 인터뷰/회의 결과를 반영하고 기능/비기능 분리. p[5]: 기능은 도입 솔루션 고유 기능에서 **추가·변경되는 기능만 작성할 수 있음**(모든 기능을 반드시 배제한다는 단정으로 확대하지 않음), 비기능은 도입 HW/SW/NW 장비 종류별 세부내역. p[7]: 전체 요구사항명과 실제 쪽수를 목차에 기록. p[8]: 시스템 구분 및 현행업무분석서의 업무영역명을 사용(원문 `영무영역명`, `현행업무분서서` 오타). p[9]: 시스템명 뒤 `AD2`와 일련번호, 예 `MES-AD2-001`. p[10]: 대표성 있는 요구사항명, 명칭 중복 금지. p[11]: 설명은 요약하여 간단히 작성. p[12]: 사업범위와 업무 담당자 면담·설문에 근거하여 정확한 의미, 프로세스, 구현 요건을 구체화. p[13]: 변경 기능은 기존 고유 기능과 변경 내용을 함께 기술. p[14]: 제약·한계·선행조건. p[15]: 유형을 기능/비기능으로 구분하고 화면/인터페이스/프로그램 존재 여부의 예시를 제시함. p[16]: 제시·협의·확인한 도입기업 담당자. p[17]: 사업계획서·착수계·회의록 등의 명확한 출처. p[18]: 이해/해결을 위한 기타 자료.

**필수 입력과 검증.** 모든 라벨을 입력 스키마에 보존하되 `기타사항` 등 적용 없음도 근거 있게 구분한다. 담당자 이름이나 실제 서명은 원자료가 있어야 한다. 요구사항 ID·명칭 유일성, AD1 업무영역 대응, 출처 존재, 유형별 목차-본문 일치, 변경 전후 서술 존재를 검사한다. `MES`는 예시이므로 사업 시스템명으로 치환한다.

**머리말·보류.** s0 p[21] 머리말은 공백만 있다. 원문의 비기능 분류 예시는 보편적인 비기능 요구사항 정의와 범위가 달라질 수 있어 **이 양식의 예시**로만 기록한다. `pageBreak=NONE` 표에 긴 내용을 넣으면 한 페이지 수용 여부를 반드시 렌더링해야 한다. 품질을 위해 상세내용을 축약해 누락시키지 말고 분할 설계나 후속 페이지 구조를 검증해야 한다. 양식은 신규/변경 건의 반복표 제목 표시·본문 유형 대단원 표시를 구체적으로 지정하지 않아 생성 정책을 별도 명시해야 한다.

## SF-AD3 기능대비표

근거: SF-AD3.json (로컬 상세근거: `analysis/stage1/analysis-design-evidence/SF-AD3.json`), 텍스트 (로컬 상세근거: `analysis/stage1/analysis-design-evidence/SF-AD3.txt`).

**용도와 구성.** 솔루션의 기준 기능을 현 사업의 기존/추가/변경/삭제 기능과 대비한다. s0 p[26] `1. 000시스템`과 동일 문단의 T2가 본문이며 별도 목차는 없다. T2 위치는 p[26]/run[1]/tbl[1], **10행×6열**, `pageBreak=CELL`, 크기 `48777×13386`, 열너비 `5585/6151/7283/3321/20018/6419`.

## 후속 단계에 넘기는 검증 조건

1. 원본 파일 해시 고정, 파일명 코드/버전과 문서 역할을 각각 식별한다. 예시 ID의 시스템 접두어는 원본 내용을 새 사업 사실로 복제하지 않는다.
2. 표지의 날짜·기업명, `000시스템`, `요구사항명n`, `화면IDn`, `프로그램IDn`, `테이블IDn`, `n+1`, 예시 쪽수 등 자리표시자를 찾아 실제 값 또는 확인 필요 상태로 관리한다. 지침 블록과 제출 본문은 경계에 따라 분리한다.
3. 표의 논리 좌표·span·물리 셀 수·크기·여백·문단/run 서식을 함께 보존한다. XML의 중복 `p.id=2147483648`을 고유 키로 사용하지 않는다. XPath/복제 블록 내 위치나 별도 안정 식별자를 사용한다.
4. AD1 현행 문제 → AD2 요구 → AD3 기능 변경 → TD1 개선흐름 → TD2 목표 구성 → TD3 화면 → TD4 프로그램 → TD5 테이블의 사실·ID·용어가 일치하는지 점검한다. 원본에 없는 참조 칼럼을 강제 추가하는 대신 공통 데이터와 검증 보고서에 관계를 기록한다.
5. 긴 요구/화면/프로그램 표, 다페이지 공정 흐름도, DB 컬럼 증가, 긴 한글명·메뉴경로에 대한 실제 한글 렌더링을 수행한다. 글자 잘림·표 겹침·서명란·머리말·쪽번호·목차 실쪽수·그림 식별성 확인을 통과해야 제출 품질을 승인할 수 있다. 이 보고서의 XML 분석은 시각 검증 완료 증거가 아니다.
