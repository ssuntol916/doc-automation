# 1단계 — 구현·시험·전환·운영·관리 양식 분석

분석일: 2026-10-24. 대상은 `_templates`의 SF-CD1, SF-TI1~4, SF-OS1~2, SF-PM1~4 11개 HWPX다. **참고자료는 열거나 비교하지 않았다. 원본 파일은 수정하지 않았다.** 이 문서는 현재 로컬 양식에 적힌 기준이며, 해당 사업의 최신 제출 규정으로 일반화하지 않는다.

## 1. 근거 읽는 법과 산출물

- `s0`, `s1`은 각각 ZIP 멤버 `Contents/section0.xml`, `Contents/section1.xml`이다.
- `Tn`은 해당 XML의 모든 `hp:tbl`을 문서순으로 센 **1기반** 번호, `RrCc`는 `hp:cellAddr`의 **0기반** 행·열 좌표다. 병합 셀은 시작 좌표로 표시한다.
- `Pn`은 해당 XML의 모든 `hp:p`를 중첩 표·머리말 문단까지 포함해 문서순으로 센 **1기반** 번호다. 원본 `hp:p/@id`는 반복되는 값이 있으므로 근거 번호로 사용하지 않는다.
- `목록`은 `_templates/스마트공장 보급·확산사업 각 단계별 개발산출물 목록_v2.0.hwpx`의 `Contents/section0.xml#T1`이다. 목록의 C3는 필수/선택, C4는 목적·내용, C5는 양식번호다.
- test-management-xml.json (로컬 상세근거: `analysis/stage1/test-management-xml.json`): 실제 경로·SHA-256, ZIP 멤버, 모든 문단 원문, 표·셀·병합·크기·여백, 글자/문단 서식 정의, 스타일 참조, 머리말 계층, 이미지 XML을 보존했다.
- [test-management-requirements.json](test-management-requirements.json): 작성 입력·반복 단위·연계·결함·보류 사항을 구분한 후속 자동화용 목록.
- `SF-*-xml-review.txt` 11개는 JSON을 사람이 읽도록 펼친 원문 목록이다. [extract-test-management.py](../../scripts/resources/tool_sources/stage1/extract-test-management.py)는 원본을 읽기만 하는 재현 스크립트다.

**구분:** 아래 `양식 명시`는 원문 규칙이다. `작성 입력`은 라벨과 명시 지침으로부터 작성 시 확보해야 하는 자료이며, 개별 항목마다 별도의 필수 표시가 있는 것은 아니다. `구현 판단`·`검증 권고`는 분석자의 제안이다. `보류`는 원문만으로 확정할 수 없는 사항이다.

## 3. 공통 구조·서식

### 3.1 실제 XML 구조

- 11개 합계 **14개 section XML, 1,196개 문단, 28개 표**. CD1·TI1·TI4는 표지/목차 `s0`와 본문 `s1`로 나뉜다. 나머지는 한 section이다.
- 모든 section의 `hp:pagePr`는 `width=59528`, `height=84188`, `landscape=WIDELY`다. 치수 기준 A4 세로에 해당한다. `hp:margin`은 좌우 5102, 위아래 4252, 머리말/꼬리말 4252, 제본 0이다. HWPUNIT 환산 시 약 좌우 18 mm, 위아래 및 머리말/꼬리말 15 mm이며, **원래 숫자와 enum을 그대로 보존**한다.
- 공통 표지는 `s0:T1`, 1×1 셀(가로46934·세로9069) 안에 사업명과 문서명이 있다. 기업명·발행일은 표 밖 문단이다. 대다수 `s0:P8/P19/P24`, PM4만 `P6/P17/P22`가 도입기업·날짜·공급기업 자리다.
- 모든 표는 `treatAsChar=1`, `flowWithText=1`, `repeatHeader=1`이다. `pageBreak`는 `CELL`이 일반적이나, TI1/TI4 시험 상세표·PM2 회의록·PM3 변경요청서는 `NONE`이다. 표 복제/확장 시 이 차이를 보존하고 실제 렌더로 판단해야 한다.
- 목차의 탭 뒤에 `1`, `2`, `n`, `n+1` 등 수동 쪽번호 문자열이 있다(CD1/TI1/TI4·TI2/TI3·OS1/OS2 총81개 `hp:t`에 inline 자식 이후 tail 존재). `t.text`만 읽으면 숫자와 일부 제목이 사라진다. 추출기는 `itertext()`로 원문을 보존한다. 목차는 기존 숫자를 그대로 재사용하지 말고 렌더 후 실제 쪽수와 맞춰야 한다.
- 개별 셀의 `header`는 전부 0이다. 따라서 `repeatHeader=1`만 보고 실제 제목 행이 반복 인쇄된다고 단정하지 않는다.
- TI2 `s0:P54`, TI3 `P51`, OS1 `P50`, OS2 `P44`에는 명시적인 문단 `pageBreak=1`이 있다. 공백 문단도 레이아웃 요소이므로 전부 일괄 삭제하면 안 된다.
- 문단 `styleIDRef`는 11개 문서의 모든 문단에서 0이다. 의미 구조가 스타일 이름에 담겨 있지 않다. `paraPrIDRef`, `charPrIDRef`, 직접 서식, 표 위치와 라벨을 함께 봐야 한다. 글자·문단 서식 ID는 파일별로 달라 공통 숫자로 치환하지 않는다.

### 3.2 타이포그래피와 작성요령의 표시

`Contents/header.xml`의 `charPr`를 실제 문단 참조로 해석한 결과다. 공통 표지 기업명은 바탕체 24 pt 굵게, 표지 사업명은 대체로 바탕체22 pt, 표지 문서명은 바탕체26 pt 굵게, 날짜는20 pt 굵게, 공급기업명은28 pt다. 기업명 문단에는 표를 수용하는 추가 run 등이 있어 단일 글자서식만으로 전체 문단을 덮어쓰면 안 된다.

| 역할 | 실제 예·서식 |
|---|---|
| CD1/TI1/TI4 본문 장제목 | `s1:P1` 바탕체13 pt 굵게, `paraPrIDRef=26` |
| CD1/TI1/TI4 시험 표 라벨 | 바탕체10 pt 굵게, `paraPrIDRef=3` |
| 일반 목차 상위/하위 | 상위 바탕체12 pt 굵게, 하위11 pt(문서에 따라 굵게/보통 혼재) |
| PM1/PM2/PM3 본문 제목 | 바탕체18 pt 굵게 |
| PM1/PM3 표 라벨 | 바탕체11 pt 굵게 |
| PM4 장제목/표 라벨 | 장제목 바탕체11 pt 굵게, 표 라벨10 pt 굵게 |
| 작성 방법 | 대체로 제목11 pt 굵게, 설명10 pt 보통 |
| 수정·추가 지침의 색 | TI2의 전환 결과 목차/본문, TI3의 추가·변경 기능 및 클라우드 설명, TI4 흐름도 지침 일부, PM3 작성 방법 전체 등에 파랑 `#0000FF`가 존재 |

색깔은 실제로 존재하는 서식이며 곧바로 제출용 내용의 색 규칙을 뜻하지 않는다. 특히 PM1 표 안의 작성 지시와 PM3 요청서의 안내 문장을 사업 사실로 남겨 두면 안 된다. 안내 문구 처리 방침은 생성 단계에서 명시적으로 분리한다.

### 3.3 표 테두리·채움

셀의 `borderFillIDRef`를 `Contents/header.xml`의 정의와 연결하면 PM4를 제외한10개는 사용된 상하좌우 테두리가 검정 실선0.12 mm다. 표지 셀 채움은 `#DFDFDF`, 시험/관리 표의 라벨 셀은 주로 `#E5E5E5`다. TI2/TI3/OS1/OS2의1셀 본문에는 별도 라벨 셀 채움이 없다. PM4는 본문 안쪽0.2 mm와 가장자리/아래쪽/헤더 위쪽0.4 mm 등이 함께 쓰이며, 헤더 셀에는0.12 mm도 섞여 있다. 단일 테두리로 초기화하면 이 구분이 사라진다. 모든 개별 정의와 적용 셀은 JSON에 보존했다.

### 3.4 이미지와 폭 검사

- PM4만 `BinData/image1.png`가 있다. 실제 `s0:P1/hp:pic`의 `hc:img/@binaryItemIDRef=image1` 및 `Contents/content.hpf`의 item과 연결된다. 추출해 확인한 이미지는 **TIPA 중소기업기술정보진흥원 로고**다. 다른10개에는 BinData가 없다.
- 본문 영역의 단순 폭 계산은 `59528-5102-5102=49324`다. PM1 T2/T3 폭51031, PM2 T2 폭49438, TI4 결함표 폭49588, CD1/TI1 결함표 폭49327로 이를 초과한다. 이것만으로 실제 잘림을 증명하지는 않지만 원본 자체의 폭·배치 재검토 대상으로 남긴다. 임의 축소하지 않는다.
- 셀 병합을 펼쳐 검사한 28개 표의 논리 격자에는 겹침·빈칸·범위초과가 없다. 이 검사는 렌더·인쇄 품질을 대신하지 않는다.

## 4. 파일별 상세 분석

### 4.1 SF-CD1 단위테스트결과서

**양식 명시**

- 구현된 기능별로 시나리오·입력 데이터·예상결과·수행결과·결함·조치 결과를 작성한다. 이번 사업의 변경/신규 기능만 작성할 수 있다(`s1:P109`). 목차에 전체 단위테스트 ID와 결함관리 내역을 쓴다(`P111`, 목차 `s0:P33~P41`).
- 기능을 식별할 이름(`P113`), 요구사항정의서의 세부요건·제약과 화면설계서의 주요 체크 사항을 확인할 화면 경로·수행 절차(`P114`), 명확한 입력 데이터(`P115`), 해당 입력에 대한 예상결과(`P116`), 실제 결과와 증적(`P117`)을 기술한다.
- 결함에는 발생 현황·원인, 해결 내용·증적을 기재한다(`P119~P120`).

**작성 입력과 반복 단위**

- 본문 `s1:T1`은 **11×6, 병합 없음**. R0 헤더: 단위테스트ID/단위테스트명/테스트시나리오/테스트데이터/예상결과/테스트결과(C0~5). R1~10은10개의 빈 작성 행이다. **반복 단위는 기능별 시험 행**으로 해석한다.10개는 양식의 준비 행 수이며 최대치라는 규정은 없다.
- `s1:T2`는 **6×6, 병합 없음**. R0 헤더: 결함번호/단위테스트ID/결함내역/발생일자/조치내역/완료일자. R1~5가 결함별 반복 행이다.
- 확보 자료: 기능/요구사항/화면 목록, 실시한 절차와 데이터, 기대값과 실행 결과, 화면 캡처 등 증적, 결함 원인·발생/완료일·해결 증거.

**연계·검증 권고**

- 목차의 시험 ID 집합 = T1 시험 ID 집합. T2의 시험 ID는 T1에 존재해야 한다.
- 요구사항의 요건/제약·화면 체크 항목이 시험 절차 및 기대값으로 연결되어야 한다. PM4의 단위시험 ID가 이 문서의 실제 ID를 가리켜야 한다.
- 완료일은 발생일 이전일 수 없으며, 조치완료 판단은 실제 증거에 근거한다. 결함이 없을 때 표를 임의 사실로 채우지 않는다.

**확인된 충돌·보류**

- `s1:P112`는 **시스템명-CD2-일련번호**, 예 `MES-CD2-001`로 안내한다. 파일명·목록은 **SF-CD1**이다. 문서 양식코드와 엔터티 ID 접두사가 반드시 같아야 한다는 규칙 자체는 없다. 따라서 과거 문구 잔존 의심으로 기록하고, CD1/CD2 중 무엇을 사용할지 사업 기준 확인 전 자동 확정하지 않는다.
- 본문에 수행일/시험자/합격 판정의 독립 열은 없다. 필요한 실무 정보이지만 양식 명시 요구로 꾸미지 않는다.

### 4.2 SF-TI1 통합테스트결과서

**양식 명시**

- 개발자 관점에서 `“2. 주요 공정별 스마트化 추진 목표 달성 상황”`의 각 공정에 대한 적용 결과를 확인한다(`s1:P71`). 이 인용 제목이 어느 외부 산출물의 어느 버전인지는 본 양식만으로 특정되지 않는다.
- 시스템명-TI1-일련번호(예 `MES-TI1-001`, `P74`), 업무를 식별할 시험명(`P75`), 공정 업무 흐름도(`P76`), 업무절차/조건별 케이스와 각 요건·제약 확인 절차(`P77`), 케이스별 입력 데이터·예상결과·실행 증적(`P78~80`)을 작성한다.
- 목차는 전체 통합시험ID와 결함관리 내역(`P73`), 결함 원인·해결·증적을 기록한다(`P82~83`).

**작성 입력·구조·반복**

- `s1:T1`은 **8×7**, `pageBreak=NONE`. R0 공정명 C1~6 병합; R1 ID 입력 C1~3 병합, 명칭 라벨 C4~5 병합, 명칭값 C6; R2 흐름도 C1~6 병합.
- R3와 R4~7의 열 구획은 **테스트케이스 C0~1 / 데이터 C2 / 예상결과 C3~4 / 결과 C5~6**이다. R4~7이4개 준비 케이스 행이다.
- 반복은 **공정·통합시험ID별 상세표**, 그 안의 **케이스별 행**, 별도 **결함별 행**으로 해석한다. 상세표는 원본 하나뿐이지만 목차의 ID1~n과 지침상 여러 시험을 전제한다.
- 결함표 `s1:T2`는 **6×6**, 병합 없음: 결함번호/통합테스트ID/결함내역/발생일자/조치내역/완료일자.
- 확보 자료: 공정별 추진목표 원문과 업무 흐름, 통합시험 시나리오·조건·결과·증거, 관련 요구사항과 단위시험, 결함 및 조치.

**연계·검증/보류**

- 공정별 추진목표 → 흐름도 → 각 케이스와 결과가 연결되는지 검사한다. PM4 통합시험 ID, 목차, 결함표의 참조는 실제 상세표 ID를 가리켜야 한다.
- 목차 `s0:P37`의 `통합테스트D4`는 다른 ID 자리(`P34~36,P39`)와 달리 I가 빠진 **명백한 자리표시 오타**다. 제출 결과는 실제 시험 목록에서 목차를 생성한다.
- 결함 없는 경우의 표기 방식, 흐름도/시험 결과의 캡션 형식·판정 기준은 양식에 없다.

### 4.3 SF-TI2 시스템전환결과서

**양식 명시 및 작성 입력**

- H/W·S/W·N/W 설치/전환 및 초기데이터 구축 결과를 **규격·설치·라이선스를 확인할 증적**과 함께 작성한다(`s0:P68`). 목차는 관련된 설치/전환·초기데이터 결과를 포함한다(`P70`).
- 설치대상: 사업계획서·착수계에 있는 품명·규격·수량(`P72`). 설치내역: 실제 설치 품명·규격·수량·상태 및 컴퓨터의 모델명·시스템정보·수량·라이선스 증거(`P73`).
- 검증: 아키텍처설계서의 검증방안을 활용한다. 시스템정보를 확인할 수 없는 장비는 규격·기능 정상 작동 여부에 대한 **도입기업 담당자 확인과 서명**을 제시한다(`P74`).
- S/W 전환: 업무영역별 프로그램 개발 본수, 물리 DB 구축 내역, 환경설정 결과 및 객관적인 전환 증적(`P75`). 클라우드 이용 시 제공내용·자원할당·전환 결과 증적(`P76`).
- 초기데이터: 사용자·거래처·원재료·완제품·코드 등 운영필수 데이터 대상(`P79`), 유형별 전환 건수(`P80`), 대상 기준 정합성·충분성 검사와 도입기업 담당자 확인(`P81`).

**구조·반복**

- 표지 T1 외에 본문은 **T2 1×1**, 셀 안11문단 `P55~P65`다. H/W 설치대상/내역/검증, S/W 설치대상/내역/전환/검증, N/W 설치대상/내역/검증, 초기데이터 대상/결과/검증의4개 영역이다. 물리적인 다열 기록표가 제공된 것이 아니다.
- 반복 단위는 장비/소프트웨어/네트워크 항목, 업무영역/프로그램·DB, 데이터 유형 및 각각의 검증·증거 블록으로 **구현 시 설계**해야 한다. 이를 원문에 없는 표 형식 고정 규칙으로 오인하지 않는다.
- 본문 앞 `P54` 강제 쪽나눔을 유지한다. 전체 목차 `P33~P52`와 본문 소제목을 동기화한다.

**연계·검증/보류**

- 계획·착수 장비의 품명/규격/수량 ↔ 아키텍처 ↔ 실제 설치·검증 증적의 대조, 프로그램 목록·DB 설계 ↔ 실제 전환 본수·건수의 대조가 필요하다.
- `P78~79`의 `기초데이터`와 목차/본문의 `초기데이터`는 용어가 혼재한다. 동일 범주인지 확인해 용어집에서 정리한다.
- `P79`의 `꼭 필요가 데이터`는 문장 오타다. 양식 원문으로 보존하되 작성 결과에 복사하지 않는다.
- 증적의 범위·서명 확보, 적용 대상이 없는 N/W/H/W 등 영역의 표기 방식은 사업 입력 없이는 결정할 수 없다. 결과·서명을 생성해서 채우지 않는다.

### 4.4 SF-TI3 메뉴얼

**양식 명시**

- 사용자용과 관리자(운영자)용을 나눈다(`s0:P69,P71`). **사용자 매뉴얼은 온라인 매뉴얼로 대체 가능**(`P72`). 사업에서 변경/추가한 기능은 누락하지 않는다(`P73`).
- 사용자용: 시스템 개요·구성도·메뉴 구조도·공통 사용방법·모든 작성 화면별 설명(`P75~81`). 화면별로 **화면명, 설명, 실행화면 캡처, 실행순서, 주요 기능/이벤트, 참고·제약**을 제시한다(`P82`).

**구조·입력·반복**

- 표지 T1 외 본문 `T2`는 **1×1**, `P52~P66`의 사용자5개·관리자6개 상위항목 틀이다. 화면별 전용 표는 없다.
- 반복은 **사용자 화면별 설명 블록**, 관리자용 S/W/장애 유형/담당자 항목이다. 목차 `P39~42`의 화면1~n을 실제 화면 목록으로 대체한다. `P51` 강제 쪽나눔을 보존한다.
- 확보 자료: 실제 화면/메뉴/권한/실행순서와 캡처, 설치·배포·운영 구성, 관리 절차, 백업/복구 결과·방법, 연락처, 온라인 대체 시 실제 접근 가능한 매뉴얼 정보.

**연계·검증/보류**

- 화면설계·기능대비표의 변경/추가 기능과 실제 매뉴얼 범위를 대조하고, 화면 캡처·버전·메뉴 경로가 실제 시스템과 일치하는지 검증한다.
- 원문 제목·파일명 `메뉴얼`과 본문 `매뉴얼` 표기가 혼재한다. 공식 문서명 식별과 정규화 명칭을 별도 저장한다.
- 온라인 대체를 허용하지만 제출물에 남길 URL·접근권한·버전·캡처·보관 방식은 양식이 정하지 않는다. 파란 글자는 지침의 실제 서식이며 기능 설명을 파랑으로 쓰라는 규칙이 아니다.

### 4.5 SF-TI4 사용자테스트결과서

**양식 명시**

- **도입기업 담당자가 운영환경에서** 공정별 스마트화 추진목표의 적용결과를 확인한다(`s1:P76`). 통합시험과 시험 주체·환경이 다르다.
- 전체 사용자시험ID와 결함관리 내역을 목차에 기재(`P78`), 업무 식별명(`P80`), 공정별 흐름도(`P81`), 업무절차·조건별 케이스와 요건/제약 확인 절차·화면 경로(`P82`), 입력 데이터·예상결과·실제 결과 증적(`P83~85`)을 작성한다.
- 결함 원인과 해결 증적을 제시한다(`P87~88`).

**작성 입력·구조·반복**

- `s1:T1`: **7×7**, `pageBreak=NONE`. R0 ID 입력 C1~3 병합, 명칭 라벨 C4~5 병합/값C6. R1 흐름도 값C1~6 병합. R2 헤더·R3~6 케이스 구획은 TI1과 같은 **2/1/2/2열 병합**이다. **통합시험과 달리 공정명 독립 행이 없다.**
- 상세표는 사용자시험ID별 반복, 그 안 케이스별 행 반복으로 해석한다.
- `s1:T2`: **6×7**, 병합 없음. 결함번호/사용자테스트ID/결함내역/발생일자/조치내역/**업무담당자/확인자**. 단위·통합시험 결함표의 완료일자를 그대로 기대하면 안 된다.
- 확보 자료: 도입기업 시험 담당자, 운영환경 식별·실행 자료, 공정 목표·흐름, 케이스/데이터/결과·증적, 결함·업무담당자·확인자.

**연계·충돌·보류**

- `s1:P79`는 **시스템명-TI5-일련번호**, 예 `MES-TI5-001`을 안내한다. 파일/목록의 SF-TI4와 충돌 가능성이 있다. ID 접두사의 확정은 보류하며, 원문과 선택한 정책을 분리 기록한다.
- 목차 `s0:P37`의 `사용자테스트D4`는 I가 빠진 자리표시 오타다.
- 지침 `s1:P87`은 업무담당자를 열거하지 않지만 실제 결함표 `T2/R0C5`에는 존재한다. **표 라벨과 지침의 합집합을 입력 요구로 보존**한다. 확인자와 업무담당자가 같아야 한다는 규칙은 없다.
- 공정명 독립 칸이 없어도 공정 목표 커버리지 확인은 필요하다. 공정과 시험 ID의 연결을 구조화 데이터에 유지할 것을 권한다. 목차·PM4·결함표 ID 참조 일치를 검사한다.

### 4.6 SF-OS1 운영지원계획서

**양식 명시**

- 지원 내용: 질의에 즉각 대응하는 헬프데스크(`P78`), 1일 로그인 수·1일 평균 사용시간·구축 기능 활용의 분석/관리 지원(`P79`), 운영 미흡 시 추가교육(`P80`)과 활성화 이벤트 계획(`P81`).

**입력·구조·반복**

**연계·보류**

- 전환결과·사용자시험 일정·OS2 운영기간과 맞춰 기간을 검증한다. 실제 지원활동은 OS2 주간 지원내역과 연결될 수 있다(구현 권고).
- 표지 사업명이 `스마트공장 구축 및 고도화 사업`(`s0:T1/R0C0 P9`)으로 다른 문서의 `보급·확산사업`과 다르다. 잘못됐다고 단정하기보다 실제 사업명으로 확정해야 할 값으로 기록한다.
- 선택 문서 포함 여부와 운영지원의 구체적 기간·지표 계산 기준은 사업별 판단이다.

### 4.7 SF-OS2 운영현황보고서

**양식 명시**

**입력·구조·반복**

- 작성 입력: 보고기간, 설치/환경설정·클라우드 자원 증적, 실제 운영 로그·등록/거래 데이터, 일별 사용자 접속기록, 주간 오류·조치·지원 기록.
- 반복은 **보고기간(주)/일자/사용자/데이터 유형/장애·지원 건**이다. 원본은 해당 데이터용 표를 제공하지 않으므로 생성 도구가 적합한 기록 블록을 설계해야 한다.

**충돌·연계·보류**

- 목차 `s0:P37`에는 `(4) 시스템 구축 현황`이 있으나 본문 T2의 구축 부분 `P45~48`에는 H/W·S/W·N/W만 있다. 또한 목차 `P39`는 `시스템 (시범)운영 및 활용 현황`, 본문 `P50`는 `시스템 (시범)운영 현황`이다. **목차와 본문 범위 차이를 명시적으로 해소**해야 한다.
- 표지 `s0:P9`의 사업명은 OS1과 같은 `구축 및 고도화 사업`이다.
- TI2의 설치/전환 결과·OS1의 지원계획 ↔ 현재 보고 현황을 대조한다. 로그인 수의 사용자 중복 제거 기준, 평균시간 산식/무활동 처리, 기준 시각은 명시되지 않아 실제 로그와 합의한 산식이 필요하다. 임의의 이용실적을 작성하지 않는다.

### 4.10 SF-PM3 변경관리내역서

**양식 명시**

- 일정·인력·요구사항·장비규격 등 변경 발생 시 사유·승인여부·공문·증빙을 관리(`s0:P122`, 목록은 사업범위도 포함).
- 대장은 요청·승인(회신) 문서정보의 목차(`P123`), 이후 **변경요청서 → 변경 사유·내용 및 양 기업이 서명한 회의록/증빙 → 전담(운영)기관 승인 공문 또는 사업관리시스템 승인/확인 캡처**를 구성한다(`P124~126`).
- 변경 사유는 객관자료(`T3/R3C1 P111`), 내용은 변경 전/후(`R4C1 P113~115`), 파급효과는 영향도를 명확히 제시(`R5C1 P117`).

**입력·구조·반복**

- T1 표지. **T2 8×8 병합 없음**: 번호/요청제목/요청공문번호/요청일/요청자/회신번호/회신내용/회신일. R1~7이 준비7행. `R1C2 P41`의 `발송된 공문번호를 기록`은 값이 아닌 작성 지시다.
- **T3 7×4**: 사업명·도입기업명, 과제번호·공급기업명, 제목·요청일(각 라벨/값 쌍), 이후 사유/내용/파급효과/비고의 값 셀은 C1~3 병합. `pageBreak=NONE`.
- 반복은 **변경 건별 대장행 + 요청서 + 근거/승인 증적 묶음**. 변경은 일정/요구사항/장비 등 여러 범위에 걸칠 수 있다.
- 확보 자료: 실제 발송·회신 식별번호와 일자/요청자, 전후 범위, 사유/영향 자료, 서명 회의록, 실제 승인/확인 증거.

**연계·결함·보류**

- 대장 ↔ 요청서 ↔ 공문/승인캡처 식별 일치; 사유/전후 변경 ↔ 개정된 요구사항·일정·인력·아키텍처; PM4 비고 ↔ 변경 근거를 검증한다.
- 머리말 `s0:P25`의 **2019년 일정계획서** 잔존은 PM2와 같다.
- 목록 분류는 선택이지만 변경 발생 시 처리 기준을 생략할 권한을 의미하지 않는다. 승인 여부는 실제 회신 문서로만 확인한다. 신청 자체를 승인으로 표시해서는 안 된다.
- 본문에 승인 상태 전용 열은 없고 회신내용을 통해 나타내는 구조다. 상태 enum과 대장/증적 연계키를 추가하는 것은 구현 판단으로 기록한다.

### 4.11 SF-PM4 요구사항추적표

**양식 명시**

- 기능은 요구사항ID를 기준으로 화면/프로그램/단위/통합/사용자시험 ID를 추적, 비기능은 결과물·추진현황을 기록한다(`s0:P136`). 한글·Excel 등 다른 형식도 허용하지만 **제시 항목을 포함**해야 한다(`P137`).
- 요구사항 ID/명/설명은 요구사항정의서 내용을 활용(`P139`), 각 요구별 관련 산출물의 ID를 명확히 기술(`P140`), 비고는 추가/변경/삭제 근거(`P141`).
- 비기능 결과물명은 실제 수행 결과물, 추진현황은 **진행중·완료·미진행**(`P143~144`).

**입력·구조·반복**

- T1 표지(위쪽 `s0:P1`에 TIPA 로고 포함), **T2 6×10 병합 없음**: 번호/요구사항ID/명/설명/화면ID/프로그램ID/단위시험ID/통합시험ID/사용자시험ID/비고. 준비5행.
- **T3 6×7 병합 없음**: 번호/요구사항ID/명/설명/결과물명/추진현황/비고. 준비5행.
- 반복 단위는 **기능 요구사항별 연결행**, **비기능 요구사항별 이행행**. 하나의 요구에 여러 화면·프로그램·시험이 대응하는 1:N/M:N 관계는 표 셀의 다중 ID 또는 행 확장 정책이 필요하다. 원문은 정확한 구분자를 지정하지 않는다.
- 입력은 확정된 AD2 요구사항 원본, 실제 설계·시험 ID 목록, 비기능 이행 결과·근거, 승인된 변경 근거다.

**연계·결함·보류**

- AD2 기능/비기능 요구 ID 집합을 누락·중복·분류오류 없이 반영하고, 표 안 ID가 실제 문서의 선언 ID에 존재하는지 검사한다. 요구명·설명은 원본과 일치시키며 근거 없이 줄이거나 의미를 바꾸지 않는다.
- ID가 존재한다고 요구가 충족된 것은 아니다. 내용·요건·제약의 설계/시험 반영과 증적을 함께 검토할 것을 권한다.
- 삭제 요구의 잔존, 변경 후 ID 재사용, 완료로 표시된 비기능에 실제 결과물 누락을 검사한다.
- 머리말 `s0:P23`에 **2019년 일정계획서** 잔존. 표지 로고는 실제 이미지이므로 복제 시 관계 item도 보존해야 한다.
- 비기능 상태 문자열은 명시돼 있으나 상태 판정 근거/담당자/기준일은 별도 필드가 없다. 관련 없는 설계/시험 열의 N/A 처리, 다중ID 표기, ID 정책 충돌(CD2/TI5) 해소는 입력 정책으로 확정할 필요가 있다.

## 6. 후속 생성/검증에 넘길 규칙

### 6.1 양식에서 직접 확인되는 내용 규칙

1. 단위시험은 세부요건·제약·화면 체크를 확인할 절차/데이터/예상값과 실제 증거를 갖춘다(CD1 s1:P114~117).
2. 통합시험은 개발자 관점의 공정 목표, 사용자시험은 도입기업 담당자·운영환경의 공정 목표를 대상으로 한다(TI1 P71, TI4 P76).
3. 시험 결함 기록은 실제 시험ID와 연결되고 원인·조치·증거를 포함한다(세 시험 문서의 결함 지침).
4. 전환 문서는 계획/착수 장비, 아키텍처 검증방안, 실제 설치·수량·라이선스·전환 및 초기데이터 검증을 증적으로 연결한다(TI2 P72~81).
5. 매뉴얼은 사용자/관리자를 구분하고 추가·변경 기능을 누락하지 않는다. 사용자는 온라인 대체가 허용된다(TI3 P71~73).
6. 운영 보고는 지표에 따라 일일/주간 단위를 구분한다(OS2 P64~67).
7. 월간 보고는 계획·실적·이슈, 변경 기록은 요청·근거·승인 증거, 추적표는 실제 요구와 설계/시험ID·비기능 결과/상태를 담는다(목록 및 PM3/PM4 지침).

### 6.2 구현 판단으로 제안하는 정합성 검사

- 공통 사업정보: 사업명·연도·과제번호·기업명·시스템명·기간의 일관성. 표지뿐 아니라 머리말·그림·첨부 캡션까지 검사한다.
- 참조 그래프: 요구사항→화면/프로그램→단위/통합/사용자시험, 시험→결함, 변경→개정 요구·설계·회의·승인 증거. N:M 관계를 데이터 모델에서 보존한다.
- 커버리지: 전체 대상에서 미검증·미문서화 항목, 변경 기능의 시험/매뉴얼 누락, 계획 장비의 전환/증거 누락을 찾는다. 제외 시 이유를 기록한다.
- 기간/수치: 일자 순서·요일·월/주 범위·집계 단위·전환 수량·실적 산식 검증. 원자료 없는 수치·서명·시험결과·승인상태를 생성하지 않는다.
- 구조: 표 좌표/병합/셀 수/참조 ID/이미지 item 관계와 HWPX ZIP 무결성 확인. 목차를 실제 엔터티 목록에서 생성한다.
- 렌더: 줄바꿈/잘림, 표 행 분할·반복제목, 장문 `pageBreak=NONE` 표, 증적 가독성·서명·쪽번호/머리말, 빈 페이지를 실제 한글 출력으로 검사한다.

### 6.3 사업 입력 없이는 확정할 수 없는 사항

접두사CD1/CD2·TI4/TI5, 최종 사업명/연도, 외부 인용 `주요 공정별 스마트化 추진 목표 달성 상황`의 원본 문서, 선택 산출물 포함 여부, 관련 없는 항목의 N/A 방식, 다중ID 표기, 진척률·평균사용시간 산식, 제출용 작성요령 제거/보관 방식, 온라인 매뉴얼 보관/접근 증거, 결함없음·미해결·승인대기 표기와 상태판정 근거다. 이를 스킬의 고정된 사실로 학습하면 안 된다.

## 7. 분석 자체의 검사 결과와 한계

11개 파일의 모든 section XML·모든 표/셀·모든 문단을 추출했다. ZIP CRC, 모든 XML well-formed 여부, 표 논리격자(병합 포함), 원본 SHA-256 불변, 요구사항 JSON에 등록한 명시적 XML 근거 참조가 실제로 존재하는지 기계적으로 검사했다. 별도 검증 결과는 test-management-validation.json (로컬 상세근거: `analysis/stage1/test-management-validation.json`)에 있다.

이번 범위는 **1단계 원본 구조·지침 분석**이다. 실제 HWPX를 한글에서 열어 페이지 단위로 출력한 결과는 아직 이 분석의 증거가 아니다. 따라서 서식의 내부 정의와 폭 위험은 확인했지만 최종 렌더 품질이 승인됐다고 주장하지 않는다. 참고문서의 문체·작성관행 비교는2단계에서 수행해야 한다.
